## discount-payment-page-no-pin — "Ad-hoc discount requires manager authorization" on prod despite a correct manager PIN, because deployed edge functions + shipped desktop client both predated the applied DB migrations
- **Date:** 2026-09-05
- **Error patterns:** Ad-hoc discount requires manager authorization, DISCOUNT_REQUIRES_MANAGER, manager PIN not prompted, discount switch, PaymentPane, /payments, process_payment_atomic, process_direct_sale_atomic, p_manager_override, p_manager_pin, deployment skew, stale edge function, Not authorized to apply a manager override, FORBIDDEN
- **Root cause(s):** Three-tier deployment skew on prod project `mkvinyekkyennyegfoxq` (Taj House of Spices) — no code defect at repo HEAD. AND-gate, both halves required: (1) prod DB had every Phase 27 migration applied (through `20260904000002`) so the atomic RPCs enforce `IF p_discount_* IS NOT NULL AND NOT p_manager_override THEN DISCOUNT_REQUIRES_MANAGER`, but prod EDGE FUNCTIONS were last deployed 2026-08-29T20:13Z (pre-Phase-27) — their Zod `BodySchema` silently strips `managerOverride`/`managerPin` and never passes `p_manager_override`, so the guard sees the parameter's `DEFAULT false` (deployed `process-payment` was worse: zero discount handling at all, dropping the /payments discount silently); (2) the newest shipped desktop release v1.2.3 predated commit `d612c10`, so the terminal displayed the manager-PIN gate but never transmitted the PIN — fixing only the server half would have flipped the error to FORBIDDEN "Not authorized to apply a manager override" rather than fixing anything.
- **Fix:** Deployment-only, no source edit. Server: `supabase functions deploy process-direct-sale process-payment process-split-payment --project-ref mkvinyekkyennyegfoxq` from repo HEAD. Client: cut release v1.2.8 from main HEAD `2f8e36a` (contains `d612c10`), version bump `e5ecac6`, built/signed by GH Actions run 33948397622, published Latest to `zedfauji/supermarket-pos-taj`; store terminal auto-updated. Verified by a real 10%-discount sale completing on the terminal.
- **Files changed:** (none — deployment-only; `src-tauri/tauri.conf.json` version bump `1.2.3 → 1.2.8` is release metadata, not a code change)
- **Why not caught:** No gate existed for this class. Nothing compares the *deployed* edge-function bundles against the *applied* migration set — `supabase db push` advances the shared remote DB from anywhere, while `supabase functions deploy` was fired from ad-hoc `.claude/worktrees/agent-*/` snapshots pinned at old commits (prod's stale bundles' `entrypoint_path` is literally `.claude/worktrees/agent-ac0c8d350d9b8fd10/…`) instead of the main checkout via `scripts/deploy-remote-backend.ps1`. A third tier — the shipped desktop tag — drifts independently again, and no release gate asserts that the newest tag contains the commits the DB contract now requires. Unit/E2E/typecheck all pass because repo HEAD is correct on all three tiers; the fault existed only in what was running.
- **Recurrence guard:** KB pattern (this entry) — for any production "server rejects a value the UI clearly collected" report, check deployed-artifact freshness on ALL tiers (`supabase functions list` `updated_at` + `entrypoint_path`, `supabase migration list`, `git tag --contains <fix-commit>`) BEFORE reading source. Follow-up not yet built (deliberate scope cut, tracked): a CI drift gate that fails when a deployed function's source hash differs from HEAD or when the newest release tag omits commits touching the RPC contract, plus banning `supabase functions deploy` from agent worktrees in favour of `scripts/deploy-remote-backend.ps1`.

## near-expiry-threshold-save — Near-expiry threshold appeared not to persist because the E2E reloaded before its asynchronous save completed
- **Date:** 2026-09-05
- **Error patterns:** near_expiry, threshold save, old value after reload, settings POST 401, auth user 403, Failed to fetch, Playwright reload race
- **Root cause(s):** The focused Playwright spec reloaded 0.766 ms after dispatching Save without waiting for the asynchronous Supabase mutation. Navigation caused `getUser()` to return 403 and sign the client out; the subsequent settings upsert ran anonymously and returned 401, leaving `near_expiry` unchanged.
- **Fix:** Wait for the Save-triggered POST to `/rest/v1/settings` and assert that its response is successful before reloading.
- **Files changed:** e2e/inventory/near-expiry-alerts.spec.ts
- **Why not caught:** Code review and the E2E contract did not require an explicit successful network response before navigation; Playwright's click auto-wait made the action look synchronized while the application mutation remained in flight.
- **Recurrence guard:** Regression test `e2e/inventory/near-expiry-alerts.spec.ts: admin saves the threshold and it persists after reload` now waits for the settings POST and asserts `response.ok()` before reload; `npx playwright test e2e/inventory/near-expiry-alerts.spec.ts --reporter=line` passes.

## inventorylog-refund-reason — Inventory > Movements tab silently renders "No log entries." for everyone once any refund lands in the last 100 stock_movements rows, because the ledger was parsed with the wrong Zod schema and one bad row aborted the whole batch
- **Date:** 2026-09-05
- **Error patterns:** No log entries, Movements tab empty, change log empty, stock_movements, InventoryLogSchema, InventoryAdjustReasonSchema, StockMovementSchema, StockMovementReasonSchema, reason='refund', ZodError invalid_enum_value, useInventoryLog, MovementsTab, resultError never read, REST 200 but UI empty, silent empty state
- **Root cause(s):** `useInventoryLog()` (src/entities/inventory/model/queries.ts) validated `stock_movements` rows with `InventoryLogSchema` instead of `StockMovementSchema` — the schema domain.ts explicitly declares for that table ("ledger table replacing inventory_log"). Two field mismatches made real rows unparseable: `reason` used the narrower `InventoryAdjustReasonSchema` (7 values, no 'refund') while the `restore_inventory_on_refund_item` trigger writes `reason='refund'` on every refund; and `productId` was non-nullable although `stock_movements.product_id` has been nullable since migration `20260426000010`. AND-gate, three necessary conditions: (1) a refund row inside the last-100 window [data]; (2) the narrow schema making `.parse()` throw [code]; (3) the fetch loop's `catch { return err(unknownError(e)) }` returning from the whole queryFn rather than skipping the row — turning one bad row into a 100-row loss [code]. A fourth condition made it invisible rather than merely broken: `MovementsTab.tsx` destructured only `{ data, isLoading }` and never read the `resultError` the hook already exposed, so every failure fell through to the "No log entries." empty state.
- **Fix:** Parse each row with `StockMovementSchema.safeParse`, skip-and-log (`inventory.log.row_parse_failed`) the offending row only, and widen the queryFn to `Result<StockMovement[]>`. `InventoryLogSchema` stays at queries.ts:382 (the adjust-inventory mutation reading back the row it just wrote — that call site controls its own input, so its narrow value space is correct). `MovementsTab.tsx` now surfaces `resultError` via StockTab.tsx:314's existing `role="alert"` pattern, suppresses the empty state while an error shows, handles the nullable `productId`, adds a 'refund' label + filter chip, and falls back to the raw reason string instead of mislabelling unknown reasons as "Manual Adjustment". Added `reasonOptionRefund` to both wAdmin catalogs.
- **Files changed:** src/entities/inventory/model/queries.ts, src/entities/inventory/model/queries.test.ts, src/widgets/InventoryPagePanel/ui/MovementsTab.tsx, src/shared/lib/i18n/locales/en-US/wAdmin.json, src/shared/lib/i18n/locales/es-MX/wAdmin.json, e2e/helpers/supabase.ts (comment only)
- **Why not caught:** Every gate passed while the feature was broken. Typecheck could not see it — the mismatch is between a Zod schema and DB *values*, and the row was cast through `any` (the file carries a blanket `no-unsafe-*` eslint-disable header). There was no unit test for `useInventoryLog()` at all. E2E could not see it either, and actively hid it: the session that DID find it live (via REST-vs-UI comparison while writing e2e/inventory/inventory-hub.spec.ts) added `delete().eq('reason','refund')` to `resetTestData` so refund fixtures never reached another spec's Movements assertions — a containment workaround that deleted the exact data that reproduced the bug, and it was left in place with a comment saying the fix was out of scope. General lesson: when a hook parses N rows in a loop, a `return` inside the `catch` is a batch-loss bug, not a row-loss bug; and a UI that drops an available `resultError` converts every backend/parse failure into an indistinguishable empty state.
- **Recurrence guard:** Regression test src/entities/inventory/model/queries.test.ts → describe('useInventoryLog'), 4 tests: "keeps a stock_movements row with reason='refund' instead of dropping the whole batch" (also covers the 'expired' narrow-enum boundary), "keeps a row whose product_id is null", "skips a genuinely malformed row without discarding the valid rows", "surfaces resultError when the fetch itself fails". Mutation-verified — reinstating the batch-abort fails test 3, reverting to InventoryLogSchema fails tests 1 and 2, so neither half of the fix can silently regress. The e2e/helpers/supabase.ts sweep comment now points at these tests and warns against using the sweep to hide a parsing bug again.
