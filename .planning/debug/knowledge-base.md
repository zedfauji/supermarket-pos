## discount-payment-page-no-pin — "Ad-hoc discount requires manager authorization" on prod despite a correct manager PIN, because deployed edge functions + shipped desktop client both predated the applied DB migrations
- **Date:** 2026-09-05
- **Error patterns:** Ad-hoc discount requires manager authorization, DISCOUNT_REQUIRES_MANAGER, manager PIN not prompted, discount switch, PaymentPane, /payments, process_payment_atomic, process_direct_sale_atomic, p_manager_override, p_manager_pin, deployment skew, stale edge function, Not authorized to apply a manager override, FORBIDDEN
- **Root cause(s):** Three-tier deployment skew on prod project `mkvinyekkyennyegfoxq` (Taj House of Spices) — no code defect at repo HEAD. AND-gate, both halves required: (1) prod DB had every Phase 27 migration applied (through `20260904000002`) so the atomic RPCs enforce `IF p_discount_* IS NOT NULL AND NOT p_manager_override THEN DISCOUNT_REQUIRES_MANAGER`, but prod EDGE FUNCTIONS were last deployed 2026-08-29T20:13Z (pre-Phase-27) — their Zod `BodySchema` silently strips `managerOverride`/`managerPin` and never passes `p_manager_override`, so the guard sees the parameter's `DEFAULT false` (deployed `process-payment` was worse: zero discount handling at all, dropping the /payments discount silently); (2) the newest shipped desktop release v1.2.3 predated commit `d612c10`, so the terminal displayed the manager-PIN gate but never transmitted the PIN — fixing only the server half would have flipped the error to FORBIDDEN "Not authorized to apply a manager override" rather than fixing anything.
- **Fix:** Deployment-only, no source edit. Server: `supabase functions deploy process-direct-sale process-payment process-split-payment --project-ref mkvinyekkyennyegfoxq` from repo HEAD. Client: cut release v1.2.8 from main HEAD `2f8e36a` (contains `d612c10`), version bump `e5ecac6`, built/signed by GH Actions run 33948397622, published Latest to `zedfauji/supermarket-pos-taj`; store terminal auto-updated. Verified by a real 10%-discount sale completing on the terminal.
- **Files changed:** (none — deployment-only; `src-tauri/tauri.conf.json` version bump `1.2.3 → 1.2.8` is release metadata, not a code change)
- **Why not caught:** No gate existed for this class. Nothing compares the *deployed* edge-function bundles against the *applied* migration set — `supabase db push` advances the shared remote DB from anywhere, while `supabase functions deploy` was fired from ad-hoc `.claude/worktrees/agent-*/` snapshots pinned at old commits (prod's stale bundles' `entrypoint_path` is literally `.claude/worktrees/agent-ac0c8d350d9b8fd10/…`) instead of the main checkout via `scripts/deploy-remote-backend.ps1`. A third tier — the shipped desktop tag — drifts independently again, and no release gate asserts that the newest tag contains the commits the DB contract now requires. Unit/E2E/typecheck all pass because repo HEAD is correct on all three tiers; the fault existed only in what was running.
- **Recurrence guard:** KB pattern (this entry) — for any production "server rejects a value the UI clearly collected" report, check deployed-artifact freshness on ALL tiers (`supabase functions list` `updated_at` + `entrypoint_path`, `supabase migration list`, `git tag --contains <fix-commit>`) BEFORE reading source. Follow-up not yet built (deliberate scope cut, tracked): a CI drift gate that fails when a deployed function's source hash differs from HEAD or when the newest release tag omits commits touching the RPC contract, plus banning `supabase functions deploy` from agent worktrees in favour of `scripts/deploy-remote-backend.ps1`.
