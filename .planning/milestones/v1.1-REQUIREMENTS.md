# Requirements: Supermarket POS

**Defined:** 2026-08-10 (v1.0) · Updated 2026-08-16 (v1.1)
**Core Value:** Fast, reliable checkout (barcode scan → cart → pay) backed by inventory that's always accurate — what's on the shelf, what's expiring, and what needs reordering — without the owner doing manual data entry for every supplier delivery.

## v1.1 Requirements — Pre-Launch Hardening

Milestone goal: close every real gap surfaced by an independent go-live audit (security exposure, broken/dead workflows, backend data-correctness bugs, deploy/ops readiness, quality debt) before this ships to the customer's store. v1.0 Alpha (15/15 requirements) is complete — see "v1.0 Requirements (shipped)" below.

### Security

- [x] **SEC-01**: The Anthropic API call (both the vision/invoice-scan pipeline in `vision.ts` and the agent chat in `brain.ts`) moves server-side into one shared Supabase Edge Function using the Bearer-auth pattern already established by `process-payment`, replacing (not duplicating) the current client-side `dangerouslyAllowBrowser` key. `@anthropic-ai/sdk` is removed from client dependencies; a build-output grep confirms no API key or SDK reference remains in the shipped bundle.
- [x] **SEC-02**: `receipt_settings` has an explicit, migration-tracked `CREATE TABLE` and `ENABLE ROW LEVEL SECURITY` with policies matching the role hierarchy — its current security posture is unauditable from migration history and must be made auditable and correct.

### Sale & Payment Workflow

- [x] **SALE-01**: The orphaned `void-order` feature is deleted end-to-end — component, edge function, RBAC `void_order` seed rows, i18n keys, and its E2E spec — while `orders.status='voided'` and any report RPCs (`get_voids_report`, `close_caja_session`) that still read that status live are left untouched.
- [x] **SALE-02**: An admin/manager can create a new staff account (name, PIN, role) through a working UI wired to the existing `create-staff` edge function; the edge function gets a caller-role check it currently lacks.
- [x] **SALE-03**: A manager can reopen a completed/paid sale and edit its line items (add/remove), using the existing `reopen_tab`/`create_order_with_items`/`remove_tab_item` RPCs — not `edit_paid_tab`, whose status guard structurally excludes reopened sales. The currently-broken E2E flow (`48-reopen-closed-ticket.spec.ts`) passes again.
- [x] **SALE-04**: The payment/checkout mutation path fails fast with a clear "you're offline, this can't be queued" message when the network is down, using the existing `isOnline()`/`networkOfflineError()` pattern — not the offline mutation queue (money-moving operations shouldn't be blindly replayed).
- [x] **SALE-05**: Refund and any remaining error paths show staff a clear, translated message instead of a raw Postgres/RPC error string.
- [x] **SALE-06**: `process-refund`'s untyped `supabase as any` cast is removed (the underlying types already exist) and the refund-items `jsonb` RPC payload gets Zod validation, since generated types don't structurally check it.

### Backend Data Integrity

- [x] **DATA-01**: `receive_shipment` no longer silently overwrites `cost_price`/`expiry_date` when a product is restocked before the prior batch sells out — a weighted-average-cost + earliest-expiry-wins formula is applied within the existing one-row-per-product model, verified not to retroactively distort historical margin reports.
- [x] **DATA-02**: `settings-backup`/`settings-restore` no longer query the dropped `pool_tables` table; both edge functions work end-to-end.
- [x] **DATA-03**: `supabase.types.ts` is regenerated to include `suppliers`/`shipments`/`receipt_settings`/`receive_shipment`.

### Ops / Deploy Readiness

- [x] **OPS-01**: The Tauri app identifier is set to the real value (`com.tajhouseofspices.supermarketpos`), replacing the placeholder `com.yourcompany.barpos`.
- [x] **OPS-02**: A documented database backup/disaster-recovery plan exists (even if it's "confirm Supabase project tier X provides Y days of PITR") so production data protection isn't silently dependent on an unconfirmed default.

### Quality Debt

- [x] **QA-01**: The Suppliers page shows a loading state during fetch and an error state on failure, instead of silently rendering blank.
- [x] **QA-02**: Storybook stories exist for the 6 core `shared/ui` primitives currently missing them (EmptyState, ConfirmDialog, POSButton, DataTable, MoneyDisplay, MoneyInput).
- [x] **QA-03**: Audit Log, Edit History, and Reports have copyable/linkable entity IDs so a manager doesn't have to manually retype a truncated ID between screens.
- [x] **QA-04**: The payment mutation hook has a dedicated unit test.

## v2 Requirements

Deferred to Beta/later milestones. Tracked but not in the v1.1 roadmap.

### AI Invoice Intake (v2/Beta)

- **AI-01**: User can drop a supplier sheet (PDF, Excel, or photo of a paper invoice) and have line items (product, qty, cost, supplier, expiry) extracted automatically
- **AI-02**: User can review and edit every extracted field before committing — no blind auto-import, since real supplier-sheet accuracy is unproven
- **AI-03**: Confirmed extracted data is written through the same receiving flow as SUP-02 (extending `agent-chat`'s vision pipeline), not a separate write path
- **AI-04**: PDF supplier sheets are parsed via native document input (the current `vision.ts` pipeline accepts PDF drops in the UI but has no PDF handling path — this is a known gap to close, not new scope)
- ~~**AI-05**: The Anthropic API call moves server-side into a Supabase Edge Function~~ — promoted to **SEC-01** in v1.1, no longer deferred

### Verification & Hardware Hardening (planned v1.2, not yet scoped)

- Automated coverage confirming barcode-scan-to-cart and manual-search-fallback work reliably (Journey 1 was previously verified working, but re-confirm after v1.1's changes land)
- Automated coverage of the receipt print/email code paths (ESC/POS command generation, email payload construction) — actual physical print output on a real Windows machine + printer needs a genuine hardware checkpoint that can't be automated from this environment
- Full client-side-secret-leak sweep beyond the Anthropic key, to confirm SEC-01's build-output grep technique catches everything

### Receipt Designer + Inventory Management Expansion (planned v1.3, not yet scoped)

- Receipt Designer: owner-configurable receipt template (logo, header/footer, line-item format) — scope not yet discussed
- Feature-rich Inventory Management subsystem beyond the current `/inventory` + `/suppliers` pages (currently product configuration lives on the Settings page) — scope not yet discussed, flagged by the customer as intended to be this POS's core differentiator
- WhatsApp receipt delivery — new feature, no existing code to build from

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Batch-level FEFO auto-allocation at sale time | One active expiry per product is sufficient for a single store; DATA-01's weighted-average-cost fix stays within the existing one-row-per-product model, not a lot-tracking system |
| Automatic PO generation / demand forecasting | Owner already knows their reorder rhythm; low-stock flag is enough signal |
| Multi-location/multi-warehouse inventory | Single store, 1-2 terminals — no current need |
| Supplier performance scorecards/analytics | A handful of known suppliers doesn't justify a dashboard nobody opens |
| PO approval workflow / status state machine | One owner, no second approver to route to |
| Accounting-system integration (QuickBooks/Tally/etc.) | No accounting system currently in place to integrate with; CSV export is sufficient |
| Counter/hanging scale hardware integration | Catalog is majority pre-packaged goods; loose-weight volume unconfirmed — revisit after Alpha usage data |
| Full 3-way match (PO vs. receipt vs. invoice) with variance workflow | This store's real flow is "goods arrive with an invoice, receive what arrived" — a single receiving confirm step is sufficient |
| Loyalty/rewards program, coupon/promotion engine | No evidence this store needs one; was already the bar-pos promotions engine being stripped in this pivot |
| Bar/pool-parlour features (tabs, pool tables, KDS, kitchen prep, waitlist, Rappi delivery, recipes/combos, ingredient costing) | Not relevant to a grocery store; stripped from the codebase in Phase 1 |
| `transfer_tab` RBAC action | Bar-pos-only concept, already absent from code; confirmed not needed for this product |
| Extending the offline mutation queue to payments (SALE-04) | Financial-correctness risk — a fail-fast guard is safer than blindly replaying a charge |
