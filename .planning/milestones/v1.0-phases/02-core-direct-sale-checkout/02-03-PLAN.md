<task type="checkpoint:decision" gate="blocking">
  <decision>How should `inventory.quantity_on_hand` be decremented for a loose-weight (kg/g) sale?</decision>
  <context>
    The existing `decrement_inventory_on_order_item()` trigger (current live body in `supabase/migrations/20260424000001_stock_movements.sql`) decrements `inventory.quantity_on_hand` by `NEW.quantity` — a whole-unit integer. It has no branch for a weight-sold product, and nothing in this codebase defines what `quantity_on_hand` should MEAN for a product sold by weight (grams? Not specified anywhere today). This is a genuine specification gap (RESEARCH.md Open Question 1 / Assumption A2), not an implementation detail — whichever option ships, real sales will start accumulating stock-movement history under that semantic the moment this migration lands, and switching later requires a second migration PLUS a data reconciliation of every already-sold weight-based line. This is a one-way door.
  </context>
  <options>
    <option id="gram-accurate">
      <name>Option A — Gram-accurate decrement (recommended)</name>
      <pros>`inventory.quantity_on_hand` for a `sold_by_weight=true` product means "grams on hand," decremented by the exact `weight_grams` sold each time. Stock is correct from day one — no known-gap to carry into Phase 3 (INV-01 "real-time stock on-hand" would otherwise be visibly wrong for every loose-weight product sold in Phase 2). The implementation cost is small: one `IF sold_by_weight THEN ... ELSE ...` branch added to two existing trigger functions (decrement + restore), not a rewrite.</pros>
      <cons>`inventory.quantity_on_hand`'s unit becomes product-type-dependent (units for regular products, grams for weight-sold ones) — anything that later sums or compares this column ACROSS product types without checking `products.sold_by_weight` first would be wrong. This must be documented in-schema (a `COMMENT ON COLUMN`) and flagged for whoever builds Phase 3's stock-aggregation/report RPCs.</cons>
    </option>
    <option id="placeholder-unit">
      <name>Option B — Placeholder 1-unit decrement, defer precision to Phase 3</name>
      <pros>No trigger change needed this phase — `quantity` stays the existing `1` sentinel for every weight line and the existing trigger decrements by 1 unconditionally. Zero new SQL branching risk.</pros>
      <cons>`inventory.quantity_on_hand` for every loose-weight product is WRONG starting the first Phase-2 sale (decrements by 1 "unit" regardless of whether 0.05kg or 5kg was sold) — a real, visible gap against INV-01 ("real-time stock on-hand") the moment Phase 3 ships. Fixing it later requires a second migration AND reconciling/backfilling every already-decremented-wrong row from Phase 2's sales history — a genuinely harder retrofit than building it correctly now.</cons>
    </option>
  </options>
  <resume-signal>Select: gram-accurate or placeholder-unit</resume-signal>
</task>
