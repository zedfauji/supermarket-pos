<objective>
Close the CHK-03/CHK-04 verification blockers from `.planning/phases/02-core-direct-sale-checkout/02-VERIFICATION.md` (CR-02, CR-03, WR-02 in `02-REVIEW.md`): `process_direct_sale_atomic` currently accepts a client-supplied payment amount and an unvalidated shift/Caja session, and returns success whenever the nested payment RPC returns `ok:true` — even when the payment only partially covers the sale or targets a closed register / another cashier's shift. This plan makes the RPC require the resulting tab to actually be `paid`, and requires the Caja/shift to be open and owned by the caller, before returning success. It also restores the local Supabase dev stack (root cause of the 4 `behavior_unverified_items` for CHK-01/02/04/05 recorded in VERIFICATION.md) and strengthens `e2e/50-direct-sale-checkout.spec.ts` per WR-02 so it actually proves the paid-tab/payment-amount invariant instead of only UI receipt visibility.

Purpose: A cashier must never see "sale complete" (and inventory must never decrement) unless a real, sufficient, correctly-attributed payment was recorded — this is the CHK-03 atomicity guarantee the phase goal depends on.
Output: A migration that tightens `process_direct_sale_atomic`'s payment/attribution invariants, an updated client-side error-code mapping, a working local E2E environment, and a strengthened + adversarial-case-covered `e2e/50-direct-sale-checkout.spec.ts`.
</objective>
