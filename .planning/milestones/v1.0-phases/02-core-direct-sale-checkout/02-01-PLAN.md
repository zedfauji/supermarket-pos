<objective>
Rebuild `/pos` as a direct-sale checkout screen and prove the entire scan/search → cart → atomic cash payment → receipt → confirm path end-to-end on one new atomic RPC, before any expansion feature (barcode scan, category grid, loose-weight, hold/resume — Plans 02-02/02-03) is layered on top.

Per CONTEXT.md's Claude's-Discretion note and RESEARCH.md Open Question 3: this plan does NOT rename the `tabs`/`orders`/`order_items` schema. **Assumption-Delta decision: no-change** — direct-sale checkout reuses `tabs`/`orders`/`order_items` as the single primary abstraction (a direct sale is "a tab that gets exactly one order, created and paid in the same breath," RESEARCH.md's own framing); renaming would mirror the documented `pool_tables → resources` fragility precedent (CONCERNS.md) for zero functional benefit. UI/i18n copy says "Sale"/"Checkout"; the DB stays `tabs`/`order_items` underneath, with `tabs.customer_name` holding the placeholder `'Walk-in'` for a direct sale (no named customer).

Purpose: A cashier must be able to complete a real sale — not a prototype of one. CHK-03's atomicity requirement ("cart total, payment record, and stock decrement all commit together — or none do") is the one thing most likely to be gotten wrong by copying the bar-tab flow's two-call pattern (RESEARCH.md Pitfall 1), so this plan builds the correct one-transaction pattern first and proves it with a real E2E run before any other feature depends on it.

Output: `/pos` reachable from Home, a working search-based add-to-cart, and cash/card/split-tender payment that is genuinely atomic with stock decrement and idempotent on retry — verified live, not asserted.
</objective>
