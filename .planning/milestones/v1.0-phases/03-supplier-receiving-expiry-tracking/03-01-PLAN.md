## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → receive-shipment Edge Function | Untrusted client JSON (supplierId, line items, cost/qty/expiry) crosses here |
| Edge Function → receive_shipment RPC (SECURITY DEFINER) | Runs with elevated (table-owner) privileges, bypassing RLS entirely |
| Browser → suppliers/supplier_products (direct client writes) | Untrusted client JSON for supplier CRUD and D-02 join-table sync crosses here, gated only by RLS |
| Browser → quick-add product (`useMutationCreateProduct`) | Untrusted client JSON creating a new sellable catalog row mid-receiving |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-03-01 | Elevation of Privilege | `receive_shipment` RPC | high | mitigate | RPC is SECURITY DEFINER and bypasses RLS — without an explicit check, any authenticated staff member (including cashier) could call the `receive-shipment` Edge Function directly and successfully mutate stock/cost/expiry. Mitigated by an explicit `role_permissions`-backed check on `p_staff_id`'s role for the `adjust_inventory` action, first statement in the RPC body, before any write (Task 1). |
| T-03-02 | Tampering | `receive_shipment` RPC line items | high | mitigate | Client-supplied `quantity`/`cost_price` trusted without server-side bound checks would allow negative/zero quantity or negative cost to corrupt `inventory.quantity_on_hand`/`cost_price`. Mitigated by explicit `quantity > 0`/`cost_price >= 0` checks inside the RPC plus the `cost_price_non_negative` CHECK constraint on `inventory` (defense in depth). |
| T-03-03 | Elevation of Privilege | Direct RPC call bypassing the Edge Function | high | mitigate | `REVOKE ALL ... GRANT EXECUTE ... TO service_role` on `receive_shipment`, identical to every existing atomic RPC — `anon`/`authenticated` can never call it via `supabase.rpc()` directly. |
| T-03-04 | Tampering | Direct client write to `suppliers`/`supplier_products` | medium | mitigate | Gated by `role_permissions`-backed RLS (`manage_products` action) on INSERT/UPDATE/DELETE, matching the existing `products` table's own policy shape — a cashier-role client write is rejected at the RLS layer. |
| T-03-05 | Tampering | Direct client INSERT into `shipments` | medium | mitigate | No client-INSERT RLS policy exists on `shipments` at all — every row is written exclusively by the SECURITY DEFINER RPC. A direct client insert attempt is rejected by RLS (default-deny, no matching policy). |
| T-03-06 | Repudiation | Receiving has no audit trail | medium | mitigate | `record_audit('shipment.receive', ...)` is called inside the RPC's single transaction, recording supplier/item-count — matches the codebase's existing audit convention for every other atomic mutation. |
| T-03-07 | Tampering | Quick-add product (D-03) mid-receiving | low | accept | Reuses the existing, already-RLS-gated `useMutationCreateProduct` path (no new backend capability) — the same trust level as creating a product via Settings → Products today. | T-03-SC | Tampering | npm/pip/cargo installs | n/a | accept | Zero new packages introduced this phase (RESEARCH.md Package Legitimacy Audit: not applicable) — no supply-chain surface to mitigate. |
