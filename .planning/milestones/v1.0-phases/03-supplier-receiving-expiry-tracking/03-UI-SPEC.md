## Spacing Scale

Declared values (must be multiples of 4) — matches the project's existing Tailwind spacing usage (`gap-1`/`gap-2`/`gap-3`/`p-3`/`p-6`/`p-8` seen across `CartItem`, `HomeDashboard`, `InventoryPagePanel`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge inline padding (`gap-1`) |
| sm | 8px | Compact element spacing — line-item row internal gaps (`gap-2`) |
| md | 16px | Default element spacing — form field spacing (`space-y-2`→`space-y-4` for stacked FormFields), card padding (`p-3`/`p-4`) |
| lg | 24px | Section padding — dialog/sheet content padding, page section gaps (`gap-6`) |
| xl | 32px | Layout gaps — page-level column gaps (`p-8` on Home-style shells) |
| 2xl | 48px | Major section breaks — between Supplier list and Receiving history sections if co-located |
| 3xl | 64px | Not used this phase (no page-level marketing spacing needed) |

Exceptions: Touch targets on the Receiving screen and Supplier form use `POSButton`'s fixed 44/56/72px heights (not the 4px spacing scale) — this is the established touch-target contract from Phase 32/33, not a new exception.

## Typography

Matches existing project usage exactly — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 regular | 1.5 |
| Label | 14px (`text-sm`) | 500 medium (`font-medium`) | 1.5 |
| Heading | 24px (`text-2xl`, `font-heading`) | 600 semibold | 1.2 |
| Display (money/emphasis) | 20px (`text-xl`) | 400–700 (`MoneyDisplay` `lg`/`xl` sizes) | 1.2 |

Only 2 weights used per dimension-4 rule: 400 (regular, body copy/values) and 600 (semibold, headings/labels-as-emphasis). `font-medium` (500) on form labels is pre-existing project convention (`FormField.tsx`, `MoneyInput.tsx`) — treated as the label weight, not a third arbitrary weight, since it's used exclusively for the Label role.

## Color

Matches existing `--pos-*` semantic tokens (`src/app/globals.css`) — dark-mode-first, oklch-based, already used identically for low-stock/warning states elsewhere in this codebase.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--background)` / `var(--card)` | Page backgrounds, form/dialog surfaces |
| Secondary (30%) | `var(--muted)`, `var(--border)` | Table row zebra/hover, section dividers, disabled states |
| Accent (10%) | `var(--pos-accent)` (jade) | Primary CTA buttons only: "Save Supplier", "Confirm Receipt", "Add Line Item" |
| Warning (near-expiry) | `var(--pos-warning)` (amber) | `NearExpiryBadge`, near-expiry cart-line badge, near-expiry Inventory tab indicator — **not** destructive/red, since expiry is advisory not blocking (mirrors existing `tab_open_warn`/happy-hour `Zap` icon usage of the same token) |
| Destructive | `var(--destructive)` / `var(--pos-danger)` | Low-stock badge (existing, unchanged), delete-supplier confirm, remove-line-item |

Accent reserved for: the single primary submit action per screen (Supplier form save, Receiving confirm button, quick-add-product submit). Never applied to secondary actions (Cancel, Add Another Line, multi-select checkboxes).

Near-expiry vs. low-stock color distinction is deliberate and load-bearing: reusing `--pos-danger` (red) for both would make an advisory expiry signal look as urgent as an actual stock-out — the amber `--pos-warning` token already carries this exact "needs attention, not blocking" meaning in this codebase (`tab_open_warn`, happy-hour pricing indicator in `CartItem.tsx:72`).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (Supplier form) | "Save Supplier" (create) / "Save Changes" (edit) |
| Primary CTA (Receiving screen) | "Confirm Receipt" |
| Primary CTA (quick-add product, inline) | "Add Product" |
| Empty state heading (Supplier list, no suppliers) | "No suppliers yet" |
| Empty state body (Supplier list) | "Add your first supplier to start tracking deliveries and receiving shipments." |
| Empty state action | "Add Supplier" |
| Empty state heading (Receiving line items, none added) | "No items added" |
| Empty state body (Receiving line items) | "Scan a barcode or search a product to add it to this shipment." |
| Near-expiry empty state (Inventory tab, no near-expiry items) | "Nothing expiring soon" / "No products are within the near-expiry window." |
| Error state (receive_shipment fails) | "Couldn't confirm this shipment. Nothing was saved — check the line items below and try again." (all-or-nothing atomicity must be reflected in copy: no partial-save language) |
| Error state (quick-add duplicate barcode) | "This barcode is already in your catalog. Search for it instead of creating a new product." |
| Destructive confirmation (remove line item) | "Remove item: This line item will be removed from the shipment. Continue?" |
| Destructive confirmation (delete supplier) | "Delete supplier: This supplier will be removed. Products already linked to it keep their receiving history. Continue?" |
| Near-expiry badge label (count) | "{count} expiring soon" (mirrors `lowStockBadge.count` i18n key shape, new key `nearExpiryBadge.count`) |
| Near-expiry cart-line signal | "Expires {date}" or "Expires in {n} days" badge, amber, next to the product name — mirrors the happy-hour `Zap` icon placement in `CartItem.tsx` |

All copy strings above are placeholders for the `es-MX`/`en-US` i18n catalogs per CLAUDE.md's i18n policy — es-MX values must be genuine Spanish (not byte-identical, since this is net-new copy, not migrated copy), en-US values are these English strings. New keys land in the `featMgmt`/`wAdmin`/`entities` namespaces matching FSD layer per the existing namespace scheme (supplier CRUD → `featMgmt`/`wAdmin`; near-expiry badge → `entities`; receiving screen → `featMgmt`).

## UI Considerations

Applicable state considerations resolved: 9 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Supplier list (no suppliers created) | ✅ covered | Renders `EmptyState` with "No suppliers yet" copy + "Add Supplier" action (see Copywriting Contract). |
| empty | Receiving line items (none added yet) | ✅ covered | Renders `EmptyState` with "No items added" copy inside the receiving form before Confirm is enabled. |
| empty | Near-expiry list/tab and badge (no items within threshold) | ✅ covered | `NearExpiryBadge` returns `null` (mirrors `LowStockBadge`); Inventory near-expiry tab renders "Nothing expiring soon" `EmptyState`. |
| loading | Supplier list, Receiving line-item product lookup | ✅ covered | Existing `LoadingSkeletons`/`LoadingSpinner` components reused — no new loading UI pattern needed (`useQuery` `isLoading` gates render, matching `InventoryPagePanel`). |
| error | `receive_shipment` RPC failure (network, validation, partial-item reject) | ✅ covered | All-or-nothing error copy (see Copywriting Contract) — the atomic RPC guarantees no partial write, so the message never implies partial success. |
| error | Quick-add product with duplicate barcode | ✅ covered | Inline `FormField` error copy directs the cashier to search instead of retrying create (see Copywriting Contract). |
| populated | Supplier list with N suppliers, Receiving form with N line items | ✅ covered | Standard row/table rendering via `DataTable`/list-row pattern (`SupplierRow.tsx` mirrors `InventoryRow.tsx`). |
| zero-one-many | Product↔Supplier multi-select (0, 1, many products per supplier and vice versa) | ✅ covered | Checkbox multi-select (D-01/D-02) has no cardinality limit in UI — same unconstrained pattern as the existing modifier multi-select. |
| overflow | Supplier name / product name long-text in list rows and badges | 🧪 backstop | No explicit truncation rule specified by CONTEXT.md; apply existing `truncate` utility (used in `CartItem.tsx:31` for product names) to list-row title cells — visual-regression screenshot should assert no horizontal overflow at 150-char supplier/product name. |
| overflow | Receiving line-item table with many rows (10+ items in one shipment) | 🧪 backstop | No explicit max-row or scroll-container spec from CONTEXT.md/RESEARCH.md; apply `ScrollArea`/`max-h` pattern already used for the modifier checklist (`ProductForm.tsx:349`) to the line-item table body — backstop test: 15-row shipment renders without layout break. |
| partial | Receiving screen with some line items using quick-add and others using catalog search in the same shipment | ✅ covered | Both paths write into the same line-item list state; no visual distinction required between quick-added and catalog-matched rows once added (RPC treats them identically — quick-add just creates the `products` row first). |
