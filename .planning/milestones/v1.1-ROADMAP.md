# Roadmap: Supermarket POS

## Overview

v1.0 (Alpha) shipped a working pivot from a bar/pool-parlour POS to a single-store supermarket POS: a clean stripped shell, direct-sale scan→cart→pay checkout, supplier/receiving/expiry-aware inventory, and a trimmed reports set. v1.1 ("Pre-Launch Hardening") closes every real gap an independent go-live audit surfaced before this ships to the customer's store: a client-exposed Anthropic API key and an unaudited `receipt_settings` table (security), an orphaned void-order feature and three broken/incomplete sale workflows (staff creation, reopen-and-edit, offline checkout), two backend data-correctness bugs (`receive_shipment` cost/expiry overwrite, dead `pool_tables` references in backup/restore), deploy readiness (Tauri identifier, DB backup/DR plan), and quality debt (Suppliers page states, Storybook coverage, cross-linked entity IDs, a payment-hook unit test). Per this project's CLAUDE.md, every phase's verification is automated Playwright/Vitest — no manual UAT checkpoints — except the two items that are inherently config/doc facts rather than app behavior (OPS-01's Tauri identifier, OPS-02's backup/DR documentation).

**Goal**: The app is a clean supermarket POS shell — all bar/pool-parlour domain code, routes, and SQL objects (RLS, RPCs, triggers, Realtime listeners) are removed, leaving only the reusable generic retail infrastructure (auth, RBAC, caja, payments, barcode scanning, printing, AI vision, base inventory) intact and verified working.

**Success Criteria**:

  1. User navigating the app sees no bar/pool-specific screens or nav items
  2. User can still log in with PIN, see role-appropriate navigation, and clock in/out
  3. Existing E2E coverage for retained infrastructure still passes after the strip

### Phase 2: Core Direct-Sale Checkout

**Goal**: A cashier can complete an entire sale — scan or search a product, build a cart including multi-unit items, pay by cash/card/split, and print a receipt — atomically and reliably.

  4. User can print a receipt immediately after a completed sale (CHK-04)

### Phase 3: Supplier, Receiving & Expiry Tracking

**Goal**: The owner can register suppliers, receive a shipment against a supplier in one atomic confirm step, and see accurate real-time stock, low-stock, and near-expiry signals without manual reconciliation.
**Requirements**: INV-01, INV-02, INV-03, INV-04, SUP-01, SUP-02, EXP-01, EXP-02
**Success Criteria**:

  1. User can view real-time, accurate stock on-hand per product, including after a manual adjustment or a physical-count reconciliation (INV-01, INV-02, INV-03)
  2. User sees a low-stock list driven by each product's reorder point (INV-04)
  3. User can create/edit a supplier record and receive a shipment against that supplier in one atomic confirm step (SUP-01, SUP-02, EXP-01)
  4. User sees a near-expiry alert in a place visible during normal operation, not only inside Reports (EXP-02)

**Plans**: 2/2 plans executed — PHASE COMPLETE

## Phase Details

### Phase 5: Delete void-order feature

**Goal**: Users have exactly one path — refund — for reversing a completed order. The orphaned void-order feature is fully removed from the client, edge functions, RBAC, and i18n surface without breaking anything that still reads `orders.status='voided'`.
**Depends on**: Nothing new (first phase of v1.1; runs against the completed v1.0 codebase). Deliberately sequenced first to shrink the diff surface on shared files (`rbac.ts`, `edge-function-contracts.ts`) before later phases touch them.
**Requirements**: SALE-01
**Success Criteria** (what must be TRUE):

  1. No void-order button or menu action is reachable from any screen — a Playwright E2E asserts the control is absent everywhere it previously appeared
  2. The void-order edge function, its RBAC `void_order` seed rows, and its i18n keys no longer exist in the codebase — an automated grep/lint check returns zero matches, while `orders.status='voided'` and its report-RPC consumers (`get_voids_report`, `close_caja_session`) are confirmed untouched
  3. `e2e/18-void-order.spec.ts` is deleted and the full Playwright suite passes without it
  4. Reports that read `orders.status='voided'` (voids report, caja close) still pass their existing E2E coverage unchanged, proving the schema/report dependency survived the deletion
  5. `e2e/35-refund.spec.ts` still passes unchanged, confirming refund remains the sole staff-facing reversal path

**Plans**: 3/3 plans executed

### Phase 6: Security hardening

**Goal**: Users' Anthropic API usage and receipt-settings data are only ever accessed through authenticated, server-side, access-controlled paths — no client-exposed API key, no unauditable table.
**Depends on**: Phase 5 (reduces shared-file diff surface on `rbac.ts`/`edge-function-contracts.ts` before this phase touches them). Sequenced ahead of Phases 7-10 since it carries the highest blast radius (unbounded third-party billing, unaudited RLS) if under-scoped.
**Requirements**: SEC-01, SEC-02
**Success Criteria** (what must be TRUE):

  1. A build-output grep across the shipped bundle finds zero occurrences of the Anthropic API key or `@anthropic-ai/sdk` reference

### Phase 7: Backend data integrity

**Goal**: Restocking a product never silently destroys prior cost/expiry data, and the settings backup/restore edge functions work end-to-end against the current schema.
**Depends on**: Phase 6 (sequenced after security hardening per blast-radius ordering; functionally independent of it)
**Requirements**: DATA-01, DATA-02, DATA-03
**Success Criteria** (what must be TRUE):

  1. Receiving the same product twice at different cost/expiry produces a weighted-average `cost_price` and the earlier of the two expiry dates — an integration test calling `receive_shipment` twice asserts the resulting inventory row
  2. Historical margin numbers for sales completed before a restock are unchanged after that restock — a test snapshots the Product Sales Margin report before and after a `receive_shipment` call to the same product and asserts no change to prior rows
  3. `settings-backup` and `settings-restore` edge functions complete successfully end-to-end with no `pool_tables` reference, verified by an integration/E2E test exercising both functions against the current schema
  4. `supabase.types.ts` includes generated types for `suppliers`, `shipments`, `receipt_settings`, and `receive_shipment`, verified by a clean `npm run typecheck` with no remaining `as any` workaround casts for those tables (DATA-03; pulled forward from Phase 8 per D-05, 2026-08-17)
