## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (any authenticated staff session) -> `create_order_with_items` RPC | Any authenticated staff session with a valid JWT can call this RPC directly — it has no staff-role restriction by design (matches normal order-taking elsewhere in the app). The client-side `ManagerPinDialog` gate in `EditReopenedItemsPanel` is a UX control, not a new server-side authorization boundary. |
| `ManagerPinDialog` (client) -> `eligibleStaff` PIN comparison | PIN matching happens client-side against staff PINs already fetched via `useStaffList()` — not itself an auth boundary; the real authorization for `reopen_tab`/`edit_paid_tab` still happens server-side via each RPC's own role re-check. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | `EditReopenedItemsPanel`'s add-item Save path (`create_order_with_items`) | medium | accept | `create_order_with_items` intentionally has no staff-role restriction (matches normal order-taking); the new PIN gate is UX-only, identical acceptance already established for every other `ManagerPinDialog` usage (refund, reopen, edit-paid-tab) in this codebase. Not a regression introduced by this phase. |
| T-09-02 | Spoofing | `ManagerPinDialog requiredAction="reopen_tab"` reuse for the add-item PIN gate | low | mitigate | Reusing the existing manager+-only `reopen_tab` `StaffAction` (RESEARCH.md A1) keeps `canAccess` semantics identical to a dedicated action — verified via `rbac.ts`'s `MANAGER_EXTRA` set requiring no changes; a bartender-role PIN is rejected exactly as it is for the existing reopen flow. |
| T-09-03 | Tampering | `EditItemsButton` visibility gate | low | mitigate | Gate reads the live `tabs.status` via `useTab(payment.tabId)`, not a derived `payment.status` heuristic (Pitfall 3) — prevents the button showing/hiding based on stale or reopen-count-dependent payment state. |

No new package installs in this plan — no `T-*-SC` package-legitimacy row required.
