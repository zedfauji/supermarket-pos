# Phase 9 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is deliberately low-novelty. Per `09-CONTEXT.md` D-01/D-05, the new panel must look/feel like `EditPaidTabDialog` (add side) and reuse `RemoveTabItemDialog` byte-for-byte (remove side). This contract locks the values already established by those two components plus `PaymentPane`'s row-button pattern — it does not invent a new visual language.

## Spacing Scale

Declared values (must be multiples of 4), matching the existing scale used across `EditPaidTabDialog`/`RemoveTabItemDialog`/`PaymentPane`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`), badge padding |
| sm | 8px | Compact stacked spacing (`space-y-2`, `gap-2`) — row internals |
| md | 16px | Default section padding (`p-3`/`p-4`), card/row spacing |
| lg | 24px | Sheet footer/body padding (`px-6 py-4`) |
| xl | 32px | — (not used by this phase's surfaces) |
| 2xl | 48px | — (not used by this phase's surfaces) |
| 3xl | 64px | — (not used by this phase's surfaces) |

Exceptions: Touch targets on primary/destructive actions use the existing `POSButton` `touchSize` CVA variant (44/56/72px height) rather than the 8pt scale directly — e.g. `touchSize="xl"` on Save, `touchSize="large"` on Cancel, matching `EditPaidTabDialog`'s footer exactly. New "Edit items" row button on `PaymentPane` uses `size="sm"` (compact, ~32px) matching its siblings (`RefundButton`, `EditTicketButton`, `ReopenTabButton`) — not a large touch target, since it's a secondary row action, not a primary flow entry.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--background)` / `var(--card)` (oklch(0.98 0.008 85) light) | Sheet body, page background |
| Secondary (30%) | `var(--secondary)` / `var(--muted)` (oklch(0.95 0.01 80)) | Row/card backgrounds (`hover:bg-muted/30`), badges, muted labels |
| Accent (10%) | `var(--primary)` (oklch(0.5 0.1 75)) | Save/Confirm primary action button only (`POSButton` default variant) |
| Destructive | `var(--destructive)` (oklch(0.55 0.21 25)) | Remove-item buttons/text, `RemoveTabItemDialog`'s `ConfirmDialog variant="destructive"`, delta/negative `MoneyDisplay` |

Accent reserved for: the panel's primary "Save"/submit button only (`POSButton` default/`focusEmphasis="high"` variant) and the `PaymentPane` row's existing focus/active states. Every other interactive element (Cancel, per-row Remove, Add item, back arrow) uses `outline`/`ghost`/`destructive` variants, never primary accent — this matches `EditPaidTabDialog`'s existing button variant choices exactly, no new accent usage introduced.

## Copywriting Contract

Reuses the `featOrders`/`wPanels` i18n namespaces per CLAUDE.md's namespace-per-FSD-layer convention (features → `featOrders`, the `PaymentPane` widget's new button → `wPanels`). New keys mirror the existing `editPaidTab`/`removeTabItem`/`reopenTab` key shapes already in `featOrders.json` — planner assigns exact key names, values below are the copy contract.

| Element | Copy |
|---------|------|
| Primary CTA (new "Edit items" row button, `wPanels`) | "Edit items" — same verb-first style as sibling buttons `Refund` / `Edit ticket` / `Reopen ticket` |
| Primary CTA (panel save action, `featOrders`) | "Save changes" — distinct from `editPaidTab.saveCorrection` ("Save correction") since this flow has no free-text "reason" field type; keep the verb+noun pattern |
| Empty state heading/body (no items on the reopened sale, edge case) | "No items on this ticket" / "Add an item below to continue." — mirrors `editPaidTab.noItems` ("No items found on this tab.") tone; reuse `editPaidTab.noItems` directly if the planner prefers zero new keys |
| Error state (add-item RPC failure) | "Could not add the item. Check your connection and try again." — verbatim pattern match to `editPaidTab.genericError` / `removeTabItem.genericError` (problem + retry instruction, translated, no raw RPC/Postgres text per SALE-05 precedent) |
| Error state (remove-item RPC failure, existing, unchanged) | Reuses `RemoveTabItemDialog`'s existing `toast.error(result.error.message)` — already translated via `useRemoveTabItem`'s error mapping (`TAB_NOT_OPEN`/`NOT_FOUND`); no new copy needed, keep as-is per D-05 |
| Destructive action: remove line item (existing, unchanged) | Reuses `removeTabItem.title` "Remove item?" / `removeTabItem.description` "This item will be permanently removed from the order. This cannot be undone." / confirm label "Remove item" — kept exactly, D-05 |
| PIN gate (add-item save, new `requiredAction`) | Reuses `managerPinGate.title` "Manager Access Required" / `managerPinGate.description` "A manager or admin PIN is required to access this section." — same shared `ManagerPinDialog` copy already used by every other PIN gate in this phase's scope, no new copy |
| Panel title/description (new Sheet, `featOrders`) | Title: "Edit items on reopened ticket" / Description: "Add or remove items on this reopened sale. Each save is recorded and manager-approved." — mirrors `editPaidTab.title`/`description` sentence structure |

## UI Considerations

Applicable state considerations resolved: 5 covered, 2 backstop, 0 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | reopened-sale item list (all items removed, none added yet) | ✅ covered | Empty-state copy defined above ("No items on this ticket") — same treatment as `EditPaidTabDialog`'s existing `tabLoading`/`noItems` empty branch, which the new panel visually inherits |
| loading | reopened-sale item list fetch | ✅ covered | Reuses `EditPaidTabDialog`'s existing `tabLoading` branch pattern ("Loading items...") — the new panel queries the same `useTab` hook, so this state is inherited, not newly built |
| error | add-item RPC failure | ✅ covered | Error copy defined above, toast pattern matches `editPaidTab.genericError` |
| error | remove-item RPC failure (`TAB_NOT_OPEN`, `NOT_FOUND`) | ✅ covered | Already handled by `useRemoveTabItem`'s existing error mapping, reused as-is per D-05 — no new copy |
| destructive-confirm | remove line item | ✅ covered | Reuses `RemoveTabItemDialog`'s existing `ConfirmDialog` copy verbatim, D-05 |
| overflow | long product name in an added/existing row | 🧪 backstop | `EditPaidTabDialog` already truncates product names in its remove-confirm row (`truncate` class) but the new panel's added-row `Select` list and existing-row label do not currently declare truncation explicitly — planner/executor should apply `truncate`/`min-w-0` consistent with the existing `RemoveTabItemDialog` row (`className="min-w-0 truncate"`); flagged as backstop since no explicit visual truncation test exists yet |
| zero-one-many | reopened sale ends with zero remaining items after all removals | 🧪 backstop | Not addressed in `09-CONTEXT.md` decisions (out of scope: "re-closing/re-paying a reopened sale" is explicitly out of scope, and this phase doesn't define what a zero-item reopened sale looks like on save) — planner should decide whether Save is disabled at zero items or left to a future phase; flagged as backstop pending planner/executor decision, not silently dropped |
