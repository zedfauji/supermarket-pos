## Interaction Contract (phase-specific, supplements template)

### Add Staff dialog (SALE-02)
1. Admin/manager clicks "Add Staff" on `StaffDashboard` (gated `ProtectedAction action="manage_staff"`, matching D-01's dialog-not-route decision) → dialog opens.
2. Fields, top to bottom: Name (`Input`, required, non-empty), PIN (`Input type="password"` or numeric — planner's call between reusing `PINKeypad` vs a plain masked `Input`; `PINKeypad` is built for auth-entry UX with dot-display, a plain `Input type="password"` matches "form" framing better since this is data entry, not PIN verification — recommend plain masked `Input` unless planner finds a stronger reason to keypad it), Confirm PIN (same field type, client-validated to match on submit per D-03), Role (`Select`, `UserRoleSchema.options`, same pattern as `EditRoleDialog` lines 125-138), Locale (`Select`, `LocaleSchema.options`, same pattern as `EditLocaleDialog` lines 87-107, defaulting to `es-MX`).
3. Submit disabled until: name non-empty, PIN/Confirm PIN both filled and equal, role selected. Locale has a default so it's never blocking.
4. On success: dialog closes, success toast fires (copy above), `StaffDashboard`'s staff list re-fetches (existing TanStack Query invalidation pattern, not new).
5. On failure (including the new caller-role rejection from D-05's edge-function auth check): generic SALE-05 fallback toast, dialog stays open so the admin can retry without re-entering the form.

### Offline-blocking dialog (SALE-04)
1. Triggered synchronously inside `useCheckoutSale.submit()` when `isOnline()` returns false, before any `fetch()`/`callProcessDirectSale` call — matching D-07's guard location.
2. Renders as a `ConfirmDialog`-based (or thin wrapper per planner's discretion, D-08 discretion note) blocking modal — visually distinct from `OfflineBanner` (which stays passively visible at the same time, unaffected).
3. "Try Again" re-invokes the same `isOnline()` check; if still offline, dialog stays open (no silent auto-retry loop, no polling — user-initiated only, per the "fail-fast guard" framing in CONTEXT.md's SALE-04 description).
4. "Cancel" closes the dialog and returns control to the cart with no side effects — the sale is not held, queued, or discarded, since D-06 scopes this to direct-sale checkout only and no offline-queue behavior was requested for this path.
