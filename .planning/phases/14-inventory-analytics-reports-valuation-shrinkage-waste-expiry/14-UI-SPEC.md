# Phase 14 — UI Design Contract

> Visual and interaction contract for Inventory Analytics Reports (Valuation, Shrinkage/Waste,
> Expiry-Loss, Turnover) plus the D-01 reason-picker capture-UI addition. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds zero new visual primitives. Every component named below already
exists in `src/shared/ui/` and is already used by sibling report panels
(`ProductSalesPanel`, `InventoryPagePanel`) on the same page. The job of this contract is to
pin *which* existing pattern each new element reuses and to lock the copy this phase introduces
— not to invent new tokens, colors, or components.

## Typography

Reuses the site's existing type roles exactly — no new sizes/weights introduced. Exactly 2 weights in this contract: 400 (regular) and 600 (semibold). No element in this phase renders at 700.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 — table cells, formula notes, DataTable content |
| Label | 12px (`text-xs`) | 400 (regular), `text-muted-foreground` | 1.4 — column headers, "unclassified adjustments" caption, group labels (existing `uppercase tracking-wide` pattern from `reports/index.tsx`'s `TabsList` group headers) |
| Heading | 24px (`text-2xl`), `font-heading` (Playfair Display) | 600 (semibold) | 1.2 — each sub-section title via reused `SectionHeader` (Valuation / Shrinkage-Waste / Expiry-Loss / Turnover) |
| Display | 30px (`text-3xl`) | 600 (semibold) — overridden from the component's 700 default | 1.2 — the store-wide valuation total only, via `MoneyDisplay size="xl" className="font-semibold"` |

**Implementation note:** `MoneyDisplay`'s `xl` size ships `font-bold` (700) by default. Its `className` prop is merged last through the existing `cn()` helper (`twMerge(clsx(inputs))` in `src/shared/lib/utils.ts`), so a caller-supplied `font-semibold` deterministically wins the Tailwind class conflict without touching `MoneyDisplay.tsx`. This phase MUST pass `className="font-semibold"` on every `MoneyDisplay size="xl"` instance it renders, holding the store-total hero figure to the same 600 weight as section headings — no third weight enters the contract.

**Primary visual anchor:** the store-wide valuation total, rendered via `MoneyDisplay size="xl"`, is the single largest and most prominent element on first load of the Inventory Analytics tab — the type scale (30px vs. 24px headings vs. 14px body) and its position at the top of the Valuation sub-section establish it as the primary focal point users land on before scanning individual report tables.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | None new — this phase is read-only reporting. The one write action (D-01's adjust-inventory dialog) keeps its existing CTA: **"Apply"** (`inventoryPagePanel.apply`), unchanged. |
| Secondary CTA | **"Export CSV"** — reused verbatim from `ExportButtons`/`inventoryPagePanel.exportCsv` pattern, extended to the 4 new report types via the existing `ExportType` union (per RESEARCH.md `Don't Hand-Roll`) |
| Empty state — Valuation | Heading: **"No inventory value to show"** / Body: **"Add products and receive stock to see valuation here."** |
| Empty state — Shrinkage/Waste | Heading: **"No shrinkage or waste recorded"** / Body: **"No qualifying stock-loss adjustments were logged in this date range."** |
| Empty state — Expiry-Loss | Heading: **"No expiry write-offs recorded"** / Body: **"No stock was written off as expired in this date range."** |
| Empty state — Turnover | Heading: **"Not enough data to compute turnover"** / Body: **"This range has no sales or no on-hand stock to compare."** |
| Error state (any report) | **"Couldn't load this report. Try again."** — reuses the existing `role="alert"` + `text-sm text-destructive` pattern from `InventoryPagePanel`'s `resultError` display, not a new error UI |
| Destructive confirmation | Not applicable — no destructive action is introduced by this phase. The reason-picker only adds selectable options to the already-gated (`adjust_inventory`, manager+) existing batch-adjust action; it does not add a new destructive flow. |
| Formula note — Valuation | **"On-hand quantity × current weighted-average cost, as of {toDate}."** + tooltip: **"Won't match Product Sales margins — Product Sales uses the cost recorded at the time of each sale; this report uses today's cost applied to current stock."** (D-03) |
| Formula note — Shrinkage/Waste | **"Value of non-sale stock loss (waste, correction, and pre-tracking adjustments), grouped by reason, {fromDate}–{toDate}."** |
| Formula note — Expiry-Loss | **"Value of product-level stock write-offs recorded as expired, {fromDate}–{toDate}."** — copy MUST NOT use "batch," "lot," or "shipment" (Pitfall 8: this system tracks one active expiry date per product, not per shipment) |
| Formula note — Turnover | **"Units sold ÷ average inventory value ({fromDate} and {toDate} reconstructed stock, averaged), {fromDate}–{toDate}."** |
| Unclassified-adjustments caption (D-02) | **"Unclassified adjustments"** row label + helper text: **"Recorded before reason tracking existed for this feature — not attributed to waste or expiry."** |
| Reason-picker label | **"Reason"** (form field label, mirrors existing `FormField` usage in the same dialog) |
| Reason-picker placeholder | **"Select a reason"** — no default selection; the field is required (categorization now feeds reporting, so silent defaulting to "Manual Adjustment" is removed) |
| Reason-picker options (exact 6, in D-01's declared order) | Waste · Expired · Delivery · Correction · Manual Adjustment · Physical Count |
| Reason-picker validation error | **"Choose a product, quantity, and reason."** — extends the existing `chooseProductAndDelta` toast copy to cover the new required field |
| Cost-unavailable fallback (Valuation/Turnover rows with no `costPrice`) | `"—"` with `aria-label="Cost unavailable — no recorded cost for this product"` — reuses `ProductSalesPanel`'s margin-unavailable fallback pattern verbatim |

## UI Considerations

Applicable state considerations resolved: 13 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Valuation / Shrinkage-Waste / Expiry-Loss / Turnover tables (list-collection) | ✅ covered | Each renders `EmptyState` with the heading+body pairs documented in Copywriting Contract, reusing the exact `EmptyState` component/props shape as `ProductSalesPanel.emptyState` |
| loading | All 4 report tables (list-collection) | ✅ covered | `LoadingSpinner` shown while the underlying query is in-flight, identical to `ProductSalesPanel`'s `if (isLoading) return <LoadingSpinner />` guard |
| error | All 4 report tables (list-collection) | ✅ covered | Query failure renders the "Couldn't load this report. Try again." copy via `role="alert"` `text-sm text-destructive`, reusing `InventoryPagePanel`'s `resultError` display pattern |
| populated | All 4 report tables (list-collection) | ✅ covered | Product-level rows + category subtotal rollup + store-wide total (Claude's Discretion default from CONTEXT.md), rendered via `DataTable`, consistent with `ProductSalesPanel`'s row shape |
| partial | Valuation / Turnover rows where `inventory.costPrice` is null (list-collection) | ✅ covered | Renders `"—"` with the cost-unavailable `aria-label`, verbatim reuse of `ProductSalesPanel`'s margin-unavailable fallback — never renders `$0.00` or blank for missing cost |
| partial | Shrinkage/Waste report, pre-Phase-14 rows with no fine-grained reason (list-collection) | ✅ covered | D-02: bucketed under the explicit "Unclassified adjustments" row, never guessed/reclassified — see Copywriting Contract |
| overflow | Formula note text under each report heading (static-content) | ✅ covered | Full formula sentence always wraps (`whitespace-normal`), never truncated/clipped — auditability (success criterion #5) requires the complete formula stay visible at all times, no ellipsis |
| overflow | Report tables with many product rows (list-collection) | ✅ covered | `DataTable`'s existing scroll/pagination behavior (unmodified), same as `ProductSalesPanel`/`InventoryPagePanel`'s stock table |
| zero-one-many | All 4 report tables (list-collection) | ✅ covered | Zero → EmptyState; one → single row, category subtotal equals the row, store total equals the row (no special-case copy needed, DataTable renders any row count uniformly); many → standard table + subtotal rollup |
| long-text | Product/category name cells (static-content, within list-collection) | ✅ covered | Existing table cell truncation (`truncate` + native `title` tooltip on hover), same pattern already in use across `DataTable` product-name columns |
| long-text | Reason-picker option labels (form) | ✅ covered | All 6 labels are short fixed strings (max "Manual Adjustment", 17 chars) — no wrap/truncate risk, no dynamic content |
| form validation | Reason-picker required field (form) | ✅ covered | Submitting without a reason selected shows the extended `"Choose a product, quantity, and reason."` toast and blocks the mutation, mirroring the existing `chooseProductAndDelta` guard in `handleBatchSubmit` |
| populated | Turnover report combining two data sources (list-collection) | ✅ covered | Row renders only when a product has data from *either* source; missing units-sold or missing inventory value renders "—" per source (not the whole row), consistent with the partial-data fallback pattern above |
| overflow | "Unclassified adjustments" bucket at scale (list-collection, edge case) | 🧪 backstop | If a store has years of pre-feature adjustment history, the unclassified bucket could dominate the Shrinkage/Waste total — no dedicated UI truncation is specified; verified at implementation time by a fixture-pinned unit test asserting the bucket renders as one aggregated row (not one row per historical movement), not a UI-visual check |
| overflow | DateRangePicker's dual meaning across sub-sections (D-05) (static-content) | 🧪 backstop | Valuation reads the range as "as of end date" while Shrinkage/Expiry/Turnover read it as a normal from/to filter — the single shared `DateRangePicker` must not visually imply one meaning for all four sections; resolved via each section's own formula note stating its specific date semantics (see Copywriting Contract), verified by an E2E assertion that the Valuation formula note renders only `{toDate}` while the other three render `{fromDate}–{toDate}` |
