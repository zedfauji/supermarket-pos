<objective>
Close the data-capture gap that Shrinkage/Waste (INVR-02) and Expiry-Loss (INVR-03) depend on:
add `expired` to the `stock_movements_reason_check` DB constraint and both domain.ts Zod enums,
then expose all 6 reason values (D-01) as a required picker on the existing manual-adjust dialog
in `InventoryPagePanel.tsx`. Without this, neither loss report has any real `expired`- or
`waste`-tagged data to aggregate — today's dialog hardcodes every adjustment to
`manual_adjustment`.

Purpose: let staff record WHY stock left the shelf (waste vs. expired vs. correction, etc.) so
the next two plans' reports have real, auditable data to roll up.
Output: a new migration, a dual-enum `domain.ts` edit, and a required 6-value reason picker on
the batch-adjust dialog.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Cashier/manager client -> `stock_movements` insert | `useMutationAdjustInventory` writes staff-supplied `reason`; the DB CHECK constraint (not the client `<select>`) is the real validation boundary against arbitrary string injection. |
| Client Zod parse -> rendered change-log | `InventoryLogSchema`/`StockMovementSchema` validate rows read back from the DB before rendering — a schema/DB mismatch (Pitfall 4) is a data-availability risk, not a confidentiality one. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-14-04 | Tampering | `reason` field on the `stock_movements` insert (`useMutationAdjustInventory`) | medium | mitigate | The client `<select>` only offers 6 values, but a hand-crafted request could still POST an arbitrary string — the `stock_movements_reason_check` CHECK constraint (this plan's migration) is the actual server-side enforcement boundary that rejects any value outside the 12-value enumerated list, matching the existing pattern for every prior reason addition (`physical_count`, etc.). |
| T-14-05 | Elevation of Privilege | Batch-adjust dialog (reason picker addition) | low | accept | The dialog is already wrapped in `ProtectedAction action="adjust_inventory"` (manager+, `InventoryPagePanel.tsx` lines 259/271) — adding picker options within an already-gated action introduces no new privilege surface; accepted as-is, no new RBAC action needed. |
| T-14-06 | Denial of Service (data integrity) | Domain.ts enum drift (Pitfall 4 — editing only one of two schemas) | high | mitigate | Task 1 edits `InventoryAdjustReasonSchema` and `StockMovementReasonSchema` in the same commit; Task 1's acceptance criteria require a `grep` match count >= 2 across both enums, and `npm run typecheck` gates the commit — an `expired` row would otherwise silently break `useInventoryLog`'s entire change-log render for every product, not just expired-tagged ones. |
</threat_model>
