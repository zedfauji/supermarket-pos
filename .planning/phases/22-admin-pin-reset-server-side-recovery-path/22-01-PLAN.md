<objective>
Give an admin a working, server-side "Reset PIN" action on the Staff page that recovers a staff
member who has genuinely forgotten their PIN and cannot log in at all — closing the gap documented
in `.planning/notes/vinty-owner-login-outage-rca.md`. A new `admin-reset-pin` Supabase Edge Function
(service-role key held server-side only, never in the Tauri client) verifies the caller is an admin,
writes `auth.users.encrypted_password` and `public.profiles.pin`/`must_change_pin` together in that
order, and is fronted by a new `AdminResetPinDialog` that reuses the existing `ManagerPinDialog`
confirm-before-fire pattern. This closes PINRST-01 through PINRST-08 (CONTEXT.md D-01..D-08) in one
plan, per this phase's coarse granularity.

Purpose: today the only fix for a genuinely forgotten PIN is a developer hand-editing
`auth.users`/`profiles` directly — a two-incident-proven failure mode that doesn't scale past a
single pilot store. This plan gives the admin an in-app, auditable, atomic-dual-write recovery path.

Output: `supabase/functions/admin-reset-pin/index.ts`, new `edge-function-contracts.ts` contract
block, a new `src/features/admin-reset-pin/` feature, `StaffDashboard.tsx` wiring, and new/extended
Playwright and Vitest coverage proving D-01 through D-08 end to end.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (authenticated staff session) -> `admin-reset-pin` Edge Function | Client-supplied JWT + request body cross into a privileged, service-role-backed function |
| Edge Function -> Supabase Auth (`auth.users`) | Privileged service-role write to the real credential store via `admin.updateUserById` |
| Edge Function -> Postgres (`profiles`) | Privileged service-role write to the `pin`/`must_change_pin` mirror |
| Browser (acting admin's own re-entered PIN, `ManagerPinDialog`) | Client-side confirm gate compared against `useStaffList()`'s cache before the network call fires |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-01 | Elevation of Privilege | admin-reset-pin role gate | critical | mitigate | Single-stage `callerProfile.role !== 'admin'` server-side check (D-01), independent of client-side RBAC hiding; proven by SM10's 403 assertions |
| T-22-02 | Elevation of Privilege | stale/cached JWT role claim of a demoted admin | medium | mitigate | Live `profiles.role` re-query on every request, never trusts the JWT's own claims — inherited unchanged from create-staff's pattern |
| T-22-03 | Tampering | dual-write partial failure (auth.users succeeds, profiles fails) | high | mitigate | `auth.users` written first; a profiles-write failure returns a distinct `PIN_RESET_PARTIAL_FAILURE`-mapped error and writes an explicit partial-failure audit entry instead of a generic one (Pitfall 1, Task 1) |
| T-22-04 | Tampering / Denial of Service | missing or inactive target not rejected | medium | mitigate | Explicit target lookup -> 404 on missing row; `is_active` guard -> 400 (D-06), enforced server-side per Pitfall 3, proven by SM11 |
| T-22-05 | Information Disclosure | raw new PIN value logged into `audit_logs.after` or edge-function logs | medium | mitigate | `recordAudit`'s `after` payload only ever carries `{ mustChangePin: true }` or the partial-failure marker object, never `newPin` |
| T-22-06 | Elevation of Privilege / Tampering | a compromised-but-authenticated admin session resets many staff PINs unattended | medium | mitigate | D-03's confirm-before-fire re-entry of the acting admin's own PIN (`ManagerPinDialog`, Task 1) adds friction on top of T-22-01's server-side gate |
