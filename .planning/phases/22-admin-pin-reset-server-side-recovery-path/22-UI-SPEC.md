# Phase 22 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note (binding):** This phase introduces zero new visual language. CONTEXT.md's
`<specifics>` section states no UI mockups were given and the user explicitly confirmed reusing
`ManagerPinDialog` chrome verbatim (D-03) rather than inventing new dialog styling. Every value
below is either (a) copied unchanged from an already-shipped component (`ManagerPinDialog`,
`CreateStaffDialog`, `StaffDashboard`'s existing action-button row) or (b) a new but structurally
identical composition of those same tokens/components for the one new surface: the
`AdminResetPinDialog`. No new colors, spacing values, font sizes, or shadcn components are
introduced.

not literal hex values in component code — no new color is introduced by this phase, so the
60/30/10 split below documents which existing tokens the new UI touches, not new values.

| Role | Value | Usage |

| Accent (10%) | `ring-primary/20` (dialog surface ring, `dialog.tsx:56`) + default `POSButton` primary variant | Reserved for: the dialog's own focus ring (inherited, untouched), and the "Reset PIN" submit button inside `AdminResetPinDialog` (primary `POSButton`, same as `CreateStaffDialog`'s "Create" button) — nothing else in this phase gets accent color |
| Destructive | `bg-destructive` (`POSButton variant="destructive"`) | **Not used for the "Reset PIN" trigger button** (see placement decision below) — reserved exclusively for genuinely destructive actions elsewhere in the app (e.g. `Clock Out`, refund); this phase's confirm-before-fire gate (D-03) is the safety mechanism, not red button styling |

Accent reserved for: the `AdminResetPinDialog` submit button ("Reset PIN") and the dialog's inherited
focus ring only — never the row-level trigger button (which stays `variant="outline"`, matching its

## Copywriting Contract

New i18n keys live in the existing `staff` namespace (matching `CreateStaffDialog`'s
`addStaff.*` keys — `StaffDashboard`'s established per-dialog key-grouping convention), under a new
`resetPin.*` group plus one new `actions.resetPin` trigger-button key. Content below is the source
value (es-MX byte-identical per this project's catalog rule; en-US is the genuine translation — do
not translate the es-MX row, only add it as the literal string shown here if it's the first
locale authored, then translate for en-US per the existing pattern). The D-03 confirm gate reuses
`featOrders:managerPinGate.*` **unchanged** — no new copy for that step.

| Element | Copy |
|---------|------|
| Row trigger button (`staff:actions.resetPin`) | "Reset PIN" — placed as a sibling `outline` `POSButton`, `size="sm"`, immediately after the existing "Force PIN Change" button and before "Edit Locale" (per RESEARCH.md Pattern 7's exact placement) |
| Dialog title (`staff:resetPin.dialogTitle`) | "Reset PIN for {{name}}" |
| Dialog description (`staff:resetPin.dialogDescription`) | "Set a new 6-digit PIN for this staff member. They'll be required to change it on their next login." |
| New-PIN field label (`staff:resetPin.newPinLabel`) | "New PIN" |
| Confirm-PIN field label (`staff:resetPin.confirmPinLabel`) | "Confirm New PIN" |
| Submit button, idle (`staff:resetPin.submit`) | "Reset PIN" |
| Submit button, pending (`staff:resetPin.submitting`) | "Resetting…" |
| Validation error — PIN mismatch (`staff:resetPin.pinMismatch`) | "PINs don't match — re-enter both fields." (reuses the exact pattern of `addStaff.pinMismatch`) |
| Collision warning, non-blocking (D-07) (`staff:resetPin.collisionWarning`) | "This PIN is already in use by {{name}}. You can still continue, but consider choosing a different PIN." |
| Success toast (`staff:resetPin.successToast`) | "PIN reset for {{name}}. They'll be asked to set a new PIN at next login." |
| Generic failure toast (`staff:resetPin.genericFailure`) | "Couldn't reset the PIN. Try again." |
| Partial-failure toast — Pitfall 1, distinct from generic failure (`staff:resetPin.partialFailureToast`) | "PIN reset partially failed — the credential changed but the staff record didn't sync. Contact support before this staff member tries to log in." (deliberately louder/longer than the generic failure copy — this is the divergence bug class the phase exists to prevent, must never render identically to a routine failure) |
| Empty state | Not applicable — no list/collection is introduced by this phase; `AdminResetPinDialog` is a form over an already-selected target staff row |
| Destructive confirmation | This phase has no delete/irreversible-data-loss action, so no red-button text-confirmation pattern applies. The equivalent safety gate is **D-03's PIN re-entry** (`ManagerPinDialog`, unchanged copy: `featOrders:managerPinGate.title`/`description`/`pinLabel`/`incorrectPin`) — do not add a second, redundant "Are you sure?" text dialog on top of it |

| error | `AdminResetPinDialog` submit (form) | ✅ covered | Three distinct toasts per the Copywriting Contract: `resetPin.pinMismatch` (client-side validation), `resetPin.genericFailure` (routine edge-function error), `resetPin.partialFailureToast` (Pitfall 1's dual-write divergence — must render as a visibly different, longer message, never collapsed into the generic-failure copy) |
| partial | `AdminResetPinDialog` form (form) | ✅ covered | Submit stays disabled until both PIN and confirm-PIN independently pass `PinSchema` AND match each other — identical gate shape to `CreateStaffDialog`'s `canSubmit` (`pin !== confirmPin \|\| !PinSchema.safeParse(...)`) |

| zero-one-many, empty, populated | — | not applicable | No `list-collection` or `media` element is introduced by this phase — the Staff page's existing table (already covered by prior phases' UI-SPECs) is untouched; `AdminResetPinDialog` is a `form` element only |
