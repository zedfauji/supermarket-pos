<objective>
Close the receipt-consistency gap RESEARCH.md's Open Question 1 flags: `process-payment` and
`process-split-payment` have the byte-identical "subtotal always equals total" bug as
`process-direct-sale` (Finding 5), but back the reopen-tab/edit-paid-tab and split-payment receipt
paths still reachable from `/payments` (`PaymentPane`). Both get the exact same fix Plan 01 already
proved on `process-direct-sale`: read `settings.billing` via the already-in-scope `admin` client, call
the same `_shared/tax.ts` `decomposeTax()`, and populate `subtotal`/`taxAmount`/`taxRatePercent`/
`taxInclusive` instead of the current `subtotal = total = amount` placeholder. No new tax math is
written here — this plan is pure wiring, reusing Plan 01's already-unit-tested pure function.

Purpose: without this plan, a store owner sees a tax line on fresh checkout receipts but not on
reopened/edited or split-payment receipts — an inconsistent, half-fixed bug that TAX-05 requires closed
across "printed/PDF/email receipts" generally, not just the direct-sale path.

Output: `process-payment`/`process-split-payment` receipts carry the same decomposed tax breakdown as
`process-direct-sale`'s, proven by extending the two existing Playwright specs that already exercise
these edge functions end-to-end against the live local Supabase stack.
