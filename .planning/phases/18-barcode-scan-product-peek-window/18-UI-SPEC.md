# Phase 18 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase renders a new OS window (architecture already locked by `18-CONTEXT.md` D-01..D-05: single persistent `"peek"` window, event-relay scan/add-to-cart, no direct cart-store access). Its content is a **pure composition of existing components** — `ProductCard`'s header pattern, `MoneyDisplay`, `StatusBadge`, `QuantityControl`, `WeightEntryDialog`, `EmptyState`, `CardSkeleton` — this is a design-system-reuse phase like Phase 16, not a new visual system. Only genuinely new surface: the window's own layout/copy and the photo-hero + detail-panel arrangement, since no screen in this app currently renders `product.imageUrl`.

## Spacing Scale

Declared values (must be multiples of 4) — matches this repo's existing Tailwind defaults, no new scale introduced:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, category-dot-to-name gap (mirrors `ProductCard`) |
| sm | 8px | Detail-row internal gaps, badge padding |

Exceptions: **44px minimum touch target** on every interactive control (`QuantityControl` buttons, footer `POSButton`s, risky-add toast action/cancel buttons) — same named exception already codified in `useConfirmRiskyAdd.ts` ("UI-SPEC Spacing Scale exception"); this phase's toast reuse inherits it verbatim, no new exception introduced.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Display (price) | 30px (`text-3xl`, `MoneyDisplay size="xl"` with `className="font-semibold"` overriding its default `font-bold` — see Weight budget below) | 600 | 1.2 |
| Heading (product name) | 24px (`text-2xl`, `font-heading`) | 600 (`font-semibold`) | 1.2 (`leading-none tracking-tight`) — mirrors `SectionHeader`'s page-title treatment |
| Label (detail-row labels, category name, stock count) | 12px (`text-xs`, `uppercase tracking-wide` for detail-row labels only) | 400 | 1.5 |
| Body (SKU/barcode values, empty/error copy) | 14px (`text-sm`) | 400 | 1.5 |

**Weight budget: exactly 2 active weights — {400, 600}.** 400 (regular) for labels, body text, and detail values; 600 (semibold) for the product-name heading and the price. `MoneyDisplay`'s built-in `xl` variant defaults to `font-bold` (700) — this phase explicitly overrides it to `font-semibold` via `className` (Tailwind-merge resolves the conflict, later class wins, same override pattern Phase 16 used on `DialogTitle`) to stay inside the 2-weight budget rather than introducing a third weight.

## Interaction Contract

### Layout (top to bottom, single scrollable column, `p-6 space-y-4`)

1. **Photo hero** — `aspect-square` (or `aspect-[4/3]`) panel, `rounded-lg border bg-muted`, `max-w-[240px]` centered. `imageUrl` present → `<img>` with `object-contain`. `imageUrl` null (the common case today — no screen in this app currently populates it) → centered `ImageOff` icon (`h-10 w-10 text-muted-foreground`) + `sr-only` "No photo available" caption.
2. **Category row** — small color dot (`h-3 w-3 rounded-full`, `category.color`) + category name (`text-xs text-muted-foreground`) — identical markup to `ProductCard`'s existing header row, reused verbatim.
3. **Product name** — `text-2xl font-heading font-semibold truncate` (Heading role). Long names truncate with `title` attribute for full-text hover, matching `ProductCard`'s `truncate` treatment.
4. **Price** — `MoneyDisplay size="xl" className="font-semibold"` directly under the name (Display role).
5. **Detail panel** — `rounded-md border bg-muted/40 p-3` (WeightEntryDialog's info-panel style, reused), two-column label/value rows: SKU, Barcode, Unit/size (`unitWeight`/`unitPiece` copy above), Stock (`StatusBadge` `inv_in_stock`/`inv_low_stock`/`inv_out_of_stock` pill + `stockCount` text). A `null` SKU/barcode row shows an em dash (`—`), not a blank cell (partial-data state, see UI Considerations).
6. **Qty/weight entry** (piece-counted only) — `QuantityControl` (existing component, unmodified), `min={1} max={99}` matching `CartItem`'s existing bounds, default `1`.
7. **Footer** — pinned bottom bar, `border-t bg-muted/50 p-4 flex gap-2 justify-end` (`DialogFooter` styling, reused). "Close" (`POSButton variant="outline" touchSize="large"`) + "Add to Cart" (`POSButton touchSize="xl"`, accent).

### Sold-by-weight path (composes `WeightEntryDialog`, does not duplicate its keypad/parsing logic)

The product detail view (steps 1-5 above, minus the piece stepper) always renders first so photo/name/price/SKU/barcode/inventory are visible even for weight products (satisfies PEEK-01 regardless of unit type). Pressing "Add to Cart" on a `soldByWeight` product opens `WeightEntryDialog` (`mode="add"`) as an overlay **on top of** the peek window's own content — identical to how `ProductGrid.selectProduct` already opens it today. Its own Confirm/Cancel buttons become the effective primary/secondary actions for that path; the peek window's outer footer is not duplicated underneath it.

**Flag for planner (data-flow, not visual):** `WeightEntryDialog`'s `confirm()` calls `addWeightedItem`/`updateWeightedItem` directly from `useCartStore` — but per D-04, the peek window has no access to the main window's cart store (separate webview/JS context; a Zustand store imported inside the peek window's own bundle is a *different* in-memory instance). Reusing `WeightEntryDialog` unmodified inside the peek window would silently write to a cart no one sees. The visual/interaction contract above (open it as an overlay, keep its existing keypad/buttons) stands regardless of how this is resolved — but the planner must decide either (a) give `WeightEntryDialog` an optional `onConfirm` override prop the peek window supplies (emits the `add-to-cart` Tauri event instead of the default store call), or (b) an equivalent thin wrapper — before wiring PEEK-03/PEEK-04 end to end. This is the one open wiring question this UI-SPEC surfaces (mirrors how Phase 16's UI-SPEC flagged a schema-level FK question it couldn't itself resolve).

### Risky-add guard (reused as-is, D-05)

Before either "Add to Cart" path commits (piece stepper confirm, or opening `WeightEntryDialog`), run `getProductRiskFlag(product)` and, if flagged, `useConfirmRiskyAdd()` exactly as `ProductGrid.selectProduct` does today — same toast copy, same `Infinity` duration, same 44px action-button minimum. Requires a `<Toaster />` (sonner) mounted in the peek window's own React root, since it's a separate render tree from the main window's existing one.

### Rescan-replaces-content (PEEK-04)

All local UI state (piece-count stepper value, any half-entered weight) is keyed on `product.id` and resets to its default the moment the displayed product changes — no stale quantity carries from one scanned product to the next.

### Not-found state

If the scanned barcode resolves to no active product, replace the entire layout above with `EmptyState` (`icon={PackageSearch}`, title = "Product not found", description = the `notFoundBody` copy above, no action button — "Close" remains available in a slim footer, "Add to Cart" is not rendered).

### Loading state

Because the peek window is a separate JS/query-cache context (per D-01..D-04), it re-fetches product data on every open/rescan rather than reading the main window's already-warm cache — treat the skeleton as a **frequent**, not rare, state. Use `CardSkeleton` (existing component) sized to roughly match the populated layout (photo block + 3 text lines) rather than a full-page spinner.

### Error state

Product-lookup query failure → replace steps 1-6 with the `loadError` copy above (`text-sm text-destructive`, centered, `p-6`); only "Close" renders in the footer.

## UI Considerations

Applicable state considerations resolved: 7 covered, 0 dismissed, 1 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Product photo, `imageUrl` null (media) | ✅ covered | `ImageOff` icon + `sr-only` "No photo available" caption — expected to be the common case, since no existing screen in this app populates `imageUrl` today |
| empty | Scanned barcode matches no product (static-content) | ✅ covered | `EmptyState` with "Product not found" / `notFoundBody`, Close-only footer |
| loading | Peek window's own product fetch (static-content) | ✅ covered | `CardSkeleton`, explicitly called out as a frequent (not rare) state per the cold-cache architecture |
| error | Peek window's own product fetch failure (static-content) | ✅ covered | Inline `text-sm text-destructive` + Close-only footer, no retry button (rescanning is the retry path) |
| populated | Full product detail (photo, name, price, SKU, barcode, unit, stock) (static-content) | ✅ covered | Layout contract above, steps 1-7 |
| partial | Product missing SKU and/or barcode (static-content) | ✅ covered | Em dash (`—`) per missing detail-row value, not a blank cell |
| long-text | Long product name (static-content) | ✅ covered | `truncate` + `title` attribute, matches `ProductCard`'s existing treatment |
| — | Weight-path cart-mutation wiring (interactive-control) | ⚠ unresolved | `WeightEntryDialog`'s built-in `addWeightedItem` call targets the wrong (peek-window-local) cart store instance under the D-04 event-relay architecture — visual/interaction shape is specified above, but the planner must resolve the store-wiring detail (see "Flag for planner" callout in Interaction Contract) before implementation |
