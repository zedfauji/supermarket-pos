## Interaction Contract

### Reprint (RCP-01, `PaymentPane` row action)

- **Placement:** `ReprintButton` is inserted as the **first** button in the row's action group (`<div className="flex items-center gap-2">`), before `EditTicketButton` — i.e., safest/most-common action leftmost, destructive action (`RefundButton`) stays rightmost. Unlike its siblings, `ReprintButton` has **no visibility gate** — it renders for every payment row regardless of `payment.isRefund`/`payment.status`, because it's a read-only action that reconstructs and reprints the whole sale's receipt (grouped by `tabId`, per RESEARCH.md Pitfall 4), not an action scoped to the specific row's tender leg.
- **Click behavior:** on click, `ReprintButton` (1) fetches `ReceiptData` via the reprint reconstruction query keyed on `payment.tabId`, (2) on success, calls `printReceipt(receiptData, settings, onRetry)` — the same shared function every other print call site uses, inheriting the retry loop (RCP-04) and toast sequence below automatically, no separate reprint-specific retry logic.
- **Busy state:** button label swaps to "Reprinting…" (`wPanels:paymentPane.reprinting`) and is `disabled` for the full duration of both the data fetch and the print call (including any retries) — prevents double-click re-entrancy on a single row.
- **Data-fetch failure (before print is attempted):** `toast.error(t('paymentPane.reprintDataFailed'))`, button returns to its resting "Reprint" label, no print attempt is made.
- **No confirmation dialog, no PIN gate** — see Copywriting Contract destructive-confirmation row.

### Print retry status (RCP-04, shared across all `printReceipt` call sites)

- **Mechanism: toast, not an inline indicator.** `printReceipt`'s `onRetry?: (attempt, max) => void` callback (RESEARCH.md Pattern 2) is wired by each caller to fire `toast.loading(...)`. Toast — not inline — is the locked choice: `printReceipt` lives in `shared/lib` and is called from 5 different UI locations (`ReceiptPreview.tsx`, `PaymentForm.tsx` ×3 fire-and-forget blocks, the new `ReprintButton`); a toast needs zero prop-drilling or per-caller UI real estate, while an inline indicator would require each of the 5 call sites to render and manage its own status element. This matches the codebase's only existing precedent for this exact class of problem (`logHardwareFail`'s `toast.error`, already fire-and-forget from the same 3 `PaymentForm.tsx` blocks).
- **Toast identity:** use a **stable `id`** per print attempt sequence (e.g. `` `print-${data.receiptNumber}` ``) across the `toast.loading` → `toast.success`/`toast.error` calls, so retries update one toast in place rather than stacking duplicate toasts — sonner's `toast.loading(msg, { id })` + `toast.success(msg, { id })` update pattern, not 3 separate toast calls.
- **Sequence:**
  1. First attempt fails → `toast.loading(t('printer.retryingPrint', { attempt: 1, max: 3 }), { id })` fires before attempt 2.
  2. Second attempt fails (3-attempt case) → `toast.loading(t('printer.retryingPrint', { attempt: 2, max: 3 }), { id })` fires before attempt 3.
  3. Final outcome:
     - Succeeds on a retried attempt → `toast.success(t('printer.printSucceededAfterRetry'), { id })`.
     - Fails on the final attempt → `toast.error(t('printer.printFailedAfterRetries', { max: 3 }), { id })`.
- **First-attempt success stays silent.** If `printReceipt` succeeds on attempt 1 (no retry needed — the overwhelming common case), **no toast fires at all**, preserving today's silent-success behavior. Only introduce toast noise when a retry sequence actually occurred — locks in D-03's "status during retry" framing as retry-triggered, not print-triggered.

### Download PDF (RCP-03, `ReceiptPreview.tsx`)

- **Placement:** 4th button added to the existing button row, positioned between `Email Receipt` and `Done` (order: Print Receipt → Email Receipt → Download PDF → Done) — primary hardware action first, delivery alternatives next, exit action last.
- **Layout:** the existing row is `flex flex-col gap-2 sm:flex-row` with each button `flex-1`; at 4 buttons this row wraps to 2 rows of 2 on narrow viewports via `flex-wrap` (add `flex-wrap` to the existing row className — do not force all 4 into one cramped row on a narrow POS panel). On `sm:` and wider, all 4 remain `flex-1` in one row, same as today's 3-button row.
- **Click behavior:** generates the PDF client-side (`receiptToPdfBytes`, per RESEARCH.md Pattern 3) then triggers the native Tauri save dialog (same `plugin-dialog`/`plugin-fs` pattern as `useExportReport.ts`). Busy state: label swaps to "Generating…" (`processPayment.generatingPdf`), `disabled` for the duration.
- **Failure:** `toast.error(t('processPayment.pdfGenerationFailed'))`, button returns to resting "Download PDF" label. This is a client-side rendering failure (not a hardware failure) — no retry loop, a single attempt is sufficient (no printer/IPC flakiness class of problem exists here).

### PDF Email Attachment Contract (RCP-03, `EmailReceiptDialog.tsx`)

- **No new form field.** The PDF attachment is **always generated and attached automatically** when a receipt email is sent — no "Attach as PDF" checkbox is added to `EmailReceiptDialog`. Rationale: RCP-03 frames PDF delivery as extending the *existing* email path ("attached to the existing email-receipt path"), not as a new user choice; a checkbox would be an extra decision on every send for a feature the owner will always want (an emailed receipt with no attachment is a strictly worse outcome than one with a PDF attached). This keeps `EmailReceiptDialog`'s form exactly as it is today (single email `Input` + Cancel/Send buttons) — zero new interactive elements on that dialog.
- **Graceful degradation, not a blocking error:** if client-side PDF generation fails while the email itself would still succeed, the email still sends (plain-text-only, matching today's exact behavior), and the success toast copy changes to make the omission visible: `toast.success(t('processPayment.receiptSentNoPdf'))` ("Receipt sent (without PDF attachment)") instead of the existing `toast.success(t('processPayment.receiptSent'))` ("Receipt sent"). This mirrors this whole phase's resilience philosophy (RCP-02: a hardware/generation failure never blocks the primary outcome) applied to the email path.
- **Ordinary success (PDF attached, no failure):** unchanged existing copy, `toast.success(t('processPayment.receiptSent'))`.
