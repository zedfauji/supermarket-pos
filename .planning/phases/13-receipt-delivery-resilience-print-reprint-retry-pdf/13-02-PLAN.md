<objective>
Give a cashier a way to reprint the receipt for any already-completed sale from the existing "Recent Payments" list in `PaymentPane` (D-01: reuses the query already powering that list — no new "last completed sale" state, and the list is already sorted most-recent-first), by reconstructing `ReceiptData` read-only from durable DB rows (it is never persisted anywhere after the original payment response is discarded — RESEARCH.md Pitfall 1) and feeding it into the same `printReceipt()` every other flow already uses, inheriting Plan 01's retry/toast behavior automatically.

Purpose: Close the "no recovery path short of re-running the whole sale" gap for paper jams/misprints.
Output: `useReceiptDataForPayment(tabId)` + `fetchReceiptDataForPayment(tabId)` in the payment entity, a new `ReprintButton` wired as the first row action in `PaymentPane`, and a green integration test plus a green E2E test proving split-sale reprint groups every leg correctly.
</objective>
