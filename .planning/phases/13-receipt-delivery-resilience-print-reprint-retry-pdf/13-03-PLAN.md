<objective>
Let a completed sale's receipt be delivered as a PDF — a standalone download from the receipt screen, and an automatic email attachment on the existing Resend send path — built by wrapping `buildThermalReceiptText`'s exact string output in one monospace PDF `<Text>` node, never by re-deriving the line-item/total structure a second time (RCP-03's explicit constraint, D-05). Both delivery paths (standalone PDF download via `@react-pdf/renderer`, and email attachment extending `send-receipt-email` to forward a base64 PDF to Resend) are built, per D-04 — not one path chosen over the other.

<assumption_delta_decision>
  <noun>receipt content formatter</noun>
  <decision>no-change</decision>
  <rationale>buildThermalReceiptText (src/shared/lib/receipt-format.ts) stays the single canonical formatter for print, email, and now PDF. The PDF wraps its exact string output in one monospace &lt;Text&gt; node rather than introducing a second, divergent table-based formatter — per RCP-03's explicit constraint ("reusing the existing receipt-format.ts formatting logic rather than a second, divergent formatter") and PATTERNS.md's explicit direction to copy exporters/pdf.tsx's plumbing (Document/Page/pdf()/docToBytes) but NOT its &lt;View&gt;/table-row layout.</rationale>
</assumption_delta_decision>

Purpose: Give the owner an archival/emailable artifact without maintaining a second layout engine or risking print/email/PDF drift.
Output: `receiptToPdfBytes`/`downloadReceiptPdf` in a new `receipt-pdf.tsx` exporter, a "Download PDF" button on `ReceiptPreview`, an automatic PDF attachment on every receipt email (with graceful degradation), and a green E2E test proving the download and email-attachment paths.
</objective>
