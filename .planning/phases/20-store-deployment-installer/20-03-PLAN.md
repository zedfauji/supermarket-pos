Auth decision (explicit reasoning, per the calling instructions — this is not a rubber-stamp): the remote
project currently has exactly one real staff account, the store owner's own admin profile ("Vinty Owner",
`must_change_pin: true`, per `.planning/notes/store-deployment-installer-decisions.md`) — its very first
login is expected to force a real PIN change for the real owner. Scripting repeated automated logins
against that account would (a) risk consuming or corrupting that first-login PIN-change moment, (b) put
the store's actual sole administrative credential in the blast radius of every future automated test run,
and (c) conflate "does the remote backend work" with "does the owner's personal account still work." This
plan instead creates one **dedicated, permanent E2E fixture admin account** (name/PIN captured in Task 1,
seeded by `scripts/seed-remote-e2e-admin.ts` in Task 2) that the spec authenticates as on every run. The
owner's real admin account is never touched by any script or spec this plan produces. Cleanup/data-safety
decisions (why receiving+checkout share one fixture product deactivated rather than deleted, why the sale
is refunded rather than left, why caja-session handling reads-before-touching) are documented inline in
each task's `<action>` below and in `<threat_model>`.
