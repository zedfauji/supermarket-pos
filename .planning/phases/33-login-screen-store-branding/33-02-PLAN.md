  <name>Task 1: Decision — store-logo bucket visibility</name>
  <decision>Should the `store-branding` Storage bucket be public-read, or private with an anonymous read grant?</decision>
  <context>
    This is the one design question in Phase 33 with no in-repo answer to copy
    (33-PATTERNS.md § "No Analog Found"). Every existing signed-URL consumer in this
    codebase — the product-photo tab, the catalog thumbnails — runs behind
    `ProtectedRoute`. The login screen does not: it renders with the anon key and no
    session, which is exactly why plan 01 had to add an anon SELECT policy just to read
    the store's name.

    The same barrier applies to the image. Phase 31's `product-photos` bucket is private
    and its `storage.objects` SELECT policy is `TO authenticated` — an anonymous caller
    cannot mint a signed URL against it. Reusing that shape unchanged would ship a login
    screen that never renders a logo.

    Why it is a one-way door: this repo ships no DOWN migrations. Changing the decision
    later means a forward migration flipping the bucket flag *and* rewriting every consumer
    between a synchronous public-URL string and an async signed-URL query with a TTL cache
    — which also changes the component's loading states.
  </context>
  <options>
    <option id="option-a">
      <name>Public-read bucket (recommended)</name>
      <pros>
        A store logo rendered on an unauthenticated screen is public by definition —
        there is nothing to keep secret from someone already looking at it.
        Strictly the tighter grant of the two: reads bypass RLS only for callers who
        already hold the exact uuid object key, and because no SELECT policy is added to
        `storage.objects`, `.list()` enumeration of the bucket stays denied for everyone.
        Collapses the client side to one synchronous string builder (`getPublicUrl`) —
        no signed-URL query, no TTL constant pair, no cache-staleness window, and none of
        the three "URL still resolving" loading states in the UI-SPEC become reachable.
        Writes remain fully gated by the `manage_settings` RLS join, unchanged.
      </pros>
      <cons>
        Diverges from Phase 31's private-bucket precedent, so the codebase will hold two
        bucket shapes. Anyone who learns an object key keeps read access to that object
        for as long as it exists (mitigated: keys are `crypto.randomUUID()`, and the
        previous object is deleted on replace).
      </cons>
    </option>
    <option id="option-b">
      <name>Private bucket with an anonymous SELECT policy</name>
      <pros>
        Mirrors Phase 31's file layout exactly, so `resolveProductImage.ts`'s TTL and
        staleTime constants carry over verbatim as CONTEXT.md's discretion section suggested.
      </pros>
      <cons>
        Broader grant, not narrower: an anon SELECT policy on `storage.objects` lets any
        anonymous caller both sign *every* object in the bucket and enumerate it with
        `.list()` — capabilities the public bucket does not hand out.
        Adds an async resolver, a TanStack Query entry, a TTL/staleTime pair and three
        loading states to serve one static image that is public anyway.
      </cons>
    </option>
  </options>
  <resume-signal>Reply "A" (or "approved" to take the recommendation) or "B".</resume-signal>
</task>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Supabase Storage (`store-branding` bucket) | Untrusted file bytes and an untrusted file name cross here. New in this plan. |
| admin browser → `settings` JSONB blob | A logo write and a text write contend for the same whole-blob upsert. |
| anonymous internet → `store-branding` object reads | Present only under checkpoint option A (public bucket). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-33-04 | Tampering | Object key derived from an uploaded file name | high | mitigate | `storeLogoObjectPath` builds the key from `crypto.randomUUID()` only; task 3's acceptance criteria grep-assert that no file-name expression appears in the module. |
| T-33-05 | Elevation of Privilege | Direct Storage API write to `store-branding`, bypassing the UI's RBAC gate | high | mitigate | `store_branding_insert`/`_update`/`_delete` each carry the `role_permissions` EXISTS join on `manage_settings`; plan 03's `store-branding-rls.spec.ts` proves cashier and anonymous denial against the database, not the UI. |
| T-33-06 | Information Disclosure | Public-read bucket (checkpoint option A) | low | accept | The object is a store logo rendered on an unauthenticated screen — public by construction. Keys are uuids and no `storage.objects` SELECT policy is added, so bucket enumeration via `.list()` stays denied. Under option B this becomes `mitigate` via the anon SELECT policy's `bucket_id` predicate. |
| T-33-07 | Denial of Service | Oversized or non-image upload | medium | mitigate | Client `validateStoreLogoFile` caps at 10 MB and allow-lists three MIME types; the bucket independently enforces `file_size_limit` 2097152 and the same `allowed_mime_types`, so a client-side bypass still hits a server-side wall. |
| T-33-10 | Tampering | Whole-blob upsert erasing sibling settings on a logo write | high | mitigate | Read-merge-write: the mutation spreads the current `general` snapshot and fails with the link error rather than writing a partial blob when that snapshot is unavailable. |
| T-33-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed by this phase (33-RESEARCH.md § Standard Stack), so the package-legitimacy gate has no applicable rows. |
