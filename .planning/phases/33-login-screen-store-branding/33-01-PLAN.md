<planner_findings>
Two findings from grounding this plan against the live code that RESEARCH.md and
PATTERNS.md did not carry, both load-bearing for STORE-02:

1. **`settings` is not readable pre-auth, and not readable by a cashier.**
   `20260510000001_rls_rewrite_phase13.sql` defines
   `settings_select_manager_admin ... FOR SELECT TO authenticated USING (get_user_role() IN ('manager','admin'))`.
   The login screen renders with the `anon` role and no session, so `useSettings()`
   returns zero rows there today. Without a new policy the login screen can never see
   `storeName` — this, not the Storage bucket, is the phase's real pre-auth blocker.

   The repo already has the exact precedent for solving it:
   `20260510000004_restore_profiles_anon_read.sql` adds
   `profiles_select_anon ... FOR SELECT TO anon USING (is_active = true)` for precisely
   this reason (the login screen's staff picker), and Phase 32's
   `20260908000001_brands_and_product_weight.sql:32` uses `FOR SELECT TO anon, authenticated`.
   This plan copies that shape, narrowed to `USING (key = 'general')`.

2. **`storeName` must drop `.min(1)`.** The current schema is
   `barName: z.string().min(1).max(120)`. D-03 requires an *unconfigured* state to be
   representable, and CONTEXT.md's Specifics note requires the stale `'Bola 8'` default
   to go. `min(1)` makes both impossible: an empty name fails `safeParse`, and
   `parseGeneral` then silently reverts the whole blob to `DEFAULT_GENERAL`. The field
   becomes `z.string().max(120).default('')`.
</planner_findings>

<assumption_delta_decision>
**Noun now primary:** *store logo* — this phase introduces a second logo concept
(`general.storeLogoPath`, Storage-backed) alongside the pre-existing receipt-only
`receipt_settings.logoDataUrl`, and a second store-name concept was avoided entirely
by renaming rather than adding.

**Decision:** `add-alongside` for the logo; `promote` for the name.

- *Name* — `promote`: `general.barName` is renamed in place to `storeName` everywhere
  (D-01/D-02). There is exactly one store-name concept after this phase; no
  pluralization survives.
- *Logo* — `add-alongside`: `logoDataUrl` (base64, thermal-printer raster, receipt-only)
  and `storeLogoPath` (Storage object, screen-rendered) stay separate, per CONTEXT.md's
  explicit out-of-scope line. They differ in encoding, storage, consumer and lifecycle;
  merging them would force one of the two into a wrong representation.

**What would later force a promote:** a third consumer needing "the store's logo"
(e.g. an emailed PDF receipt, or a printed logo sourced from the uploaded image rather
than a separately-pasted base64 one). At that point the receipt pipeline should read
`storeLogoPath` and rasterise it, and `logoDataUrl` should be retired — the housekeeping
phase CONTEXT.md already names as deferred.
</assumption_delta_decision>
