## Interaction Contract (new fields — decided, not left ambiguous)

Auto-mode assumption, recorded explicitly since RESEARCH.md's example code was "shape only":

- **Checkboxes/select (existing 6 fields + paper width):** unchanged — `onCheckedChange`/`onChange` calls `patchReceipt(...)` directly, which updates local optimistic state AND fires the mutation immediately. This is correct for discrete toggle/select values and must not change.
- **`headerLine2` / `footerText` (new, continuous text input):** calling `patchReceipt` (and therefore the network mutation) on every keystroke would spam `updateReceiptSettings.mutate` on each character. Contract: the input's `onChange` updates **local draft state only** (drives the live preview instantly, satisfies RCPD-01 criterion 2 — "reflects current unsaved edits before saving"); the persisted `patchReceipt` mutation fires on `onBlur`. This requires splitting the existing `patchReceipt` helper into a local-only setter (reused by `onChange`) and the existing mutate-triggering call (reused by `onBlur`) — both already exist as `setLocalReceipt` vs. the body of `patchReceipt`; no new state shape needed, just a new call site that skips the `mutate`.
- Both new inputs get `maxLength={48}` / `maxLength={480}` respectively (mirrors the DB/Zod caps `VARCHAR(48)`/`VARCHAR(480)`, `ReceiptSettingsSchema.headerLine2`/`footerText` — client-side UX guard; DB constraint remains the actual backstop per RESEARCH.md V5).

## Live Preview Panel — Contract

- **Renderer:** `buildThermalReceiptText(sampleReceiptData, locale, draftReceiptSettings)` — the same function/signature RESEARCH.md Pattern 1 specifies, called with the draft (unsaved, optimistic) `ReceiptSettings`, not the server-persisted value. Do not build a second renderer or a CSS approximation (RESEARCH.md Pitfall 2, explicitly named anti-pattern).
- **Container:** identical classes to `ReceiptPreview.tsx`'s existing `<pre>`: `max-h-[50vh] overflow-auto rounded-md border bg-muted/40 p-3 font-mono text-[11px] leading-tight whitespace-pre`. Reuse verbatim — do not restyle.
- **Sample data fixture:** a static, hardcoded `ReceiptData` object local to the preview component (not a network fetch) — 2 line items (one with a modifier line to exercise the modifier-line-rendering path, one plain), one payment leg (cash, with `tenderedAmount`/`changeAmount` so the tendered/change lines render), a receipt number, cashier + customer name populated (so `showCashierName`/`showCustomerName` toggles are visibly demonstrable in the preview). This is what makes the toggles' effect legible without needing a real sale.
- **Placement:** directly inside the existing `space-y-4 rounded-lg border p-4` "Receipt Settings" card, after the toggle list — single card, not a second bordered box, to avoid visual clutter on what's already a dense settings panel.
- **Footer text wrapping (explicit correction to RESEARCH.md's "shape only" example):** `footerText` is capped at 480 characters — 15x a 32-column line. RESEARCH.md's Pattern 1 code sample shows `centerLine(sanitize(settings.footerText))`, which truncates to one line and silently drops everything past the paper width. That is wrong for a field sized for multi-line content. Contract: `footerText` must wrap using the same chunking loop `buildThermalReceiptText` already uses for `barAddress` (loop `padRight(footerText.slice(i, i + LINE), LINE)` in `LINE`-sized increments), not a single `centerLine` call. Flag this explicitly to the planner/executor — do not carry the truncating example forward verbatim.
- **`headerLine2` (48 chars max, single line by design):** stays a single `centerLine(...)` call, truncated to paper width if it exceeds the current `paperWidthChars` — consistent with how the store-name header line already truncates. This is a much shorter field (48 chars, roughly one line at any paper width) so single-line truncation is the correct, unsurprising behavior — do not wrap it.
