<objective>
Make `buildThermalReceiptText` (the single shared formatter behind print/preview/email) actually read `ReceiptSettings` instead of hardcoding a 32-column width and unconditional field emission. This closes RESEARCH.md's Pitfall 1 — `receipt_settings` has been faithfully persisted since Phase 6 but never read by the code that builds receipt text — which is the load-bearing gap for RCPD-01 (per D-01/RESEARCH.md; no CONTEXT.md decisions exist for this autonomous-run phase, so all citations below are to RESEARCH.md/UI-SPEC.md findings, not user decisions).

`buildPreChequeText` (a separate, unrelated 58mm-only function in the same file) is explicitly NOT touched by this plan — it keeps using the module-level `LINE = 32` constant unchanged.

Purpose: Every other plan in this phase (call-site threading, Settings UI live preview) depends on this new 3-parameter signature existing first.
Output: `buildThermalReceiptText(receipt, locale, settings)` — settings-aware paper width, toggle-gated fields, headerLine2, and a correctly line-wrapped (not truncated) footerText.
</objective>
