# Phase 16 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds a new manager+-only feature surface (purchase orders) with no prior UI to extend — unlike Phase 15 (a form extension). CONTEXT.md explicitly deferred one open question to this pass: **page placement (new top-level route vs. tab/panel on Suppliers)**. That decision is resolved below under "Page Placement Decision." Every other visual/interaction choice mirrors existing, proven patterns in this codebase (`SupplierListPanel.tsx`, `ReceiveShipmentForm.tsx`, `StatusBadge.tsx`, `DataTable.tsx`, `ReportsRoute`) rather than inventing new ones — this is a design-system-reuse phase, not a new visual system.

---

## Page Placement Decision

**Decision: new top-level route `/purchase-orders`, not a tab/panel on the existing Suppliers page.**

Rationale:
1. **RESEARCH.md's security finding governs this.** D-02 requires cashiers to have *zero* read access to PO data, but the Suppliers page's existing `SELECT` RLS is `USING (true)` and `/suppliers` has no route-level role guard — only nav-tile hiding. Nesting PO under `/suppliers` would either (a) inherit that weaker access pattern by association, tempting a `USING (true)` policy on `purchase_orders` too, or (b) require a role guard around only *part* of an already-rendered page, which is a more error-prone shape than guarding a whole route. A dedicated route with its own `PurchaseOrdersRoute` guard (mirroring `ReportsRoute`) makes the boundary structurally obvious and matches this codebase's one existing precedent for "read access itself must be gated," not just writes.
2. **Content volume.** Suppliers page is already a single dense `SupplierListPanel` + a `ReceiveShipmentForm` dialog. PO adds a list (with status/date/total columns), a create/edit line-item form, an auto-draft-from-low-stock flow, and a receive action — enough surface area to justify its own page, consistent with how `/inventory` and `/suppliers` are already separate pages despite both being inventory-adjacent.
3. **Nav precedent.** `HomeDashboard.tsx`'s `ITEMS` array already gates tiles per-action (`adjust_inventory` for `/suppliers`/`/inventory`, `view_reports` for `/reports`). Adding one more manager-gated tile (`manage_products` → `/purchase-orders`) is the established pattern, not a new one.

**Implementation shape:**
- New route `/purchase-orders` in `src/app/router.tsx`, wrapped in a new `PurchaseOrdersRoute` guard component (`src/app/purchase-orders-route.tsx`, identical shape to `reports-route.tsx`, gated on `can('manage_products')`).
- New `HomeDashboard.tsx` tile: `{ path: '/purchase-orders', labelKey: 'homeDashboard.tiles.purchaseOrders', icon: ClipboardList, requiredAction: 'manage_products', managerLabelKey: 'homeDashboard.managerLabels.manager' }` — placed immediately after the existing `/suppliers` tile (adjacent in the grid, since they're workflow-adjacent). **Icon note:** `ClipboardList` is already imported in `HomeDashboard.tsx` for `/audit`; reuse `Package` variant is taken by `/inventory` — use `FileText` (not yet used in this file) for the Purchase Orders tile to keep icons visually distinct.
- **Cross-link, not merge:** add a small secondary link/button on the existing Suppliers page ("View Purchase Orders" or similar, `variant="outline"`) so the two related workflows are discoverable from each other without collapsing into one page. This is optional polish, not required for PO-01..03's success criteria — the executor may omit it if time-constrained; the dedicated route is the only non-negotiable part of this decision.

## Interaction Contract

Decided, not left ambiguous — this phase introduces new flows (auto-draft, receive-from-PO) with no direct prior-phase precedent to copy verbatim, unlike Phase 15's field-level extension.

### PO lifecycle (two states, per CONTEXT.md's discretion note)
- **`draft`** → **`received`**. No intermediate "submitted/ordered" state — the requirements only name these two. A draft PO is fully editable (add/remove/edit lines, change supplier). A received PO is **read-only** in the detail view — no editing, no re-receiving (RPC-level `PO_ALREADY_RECEIVED` guard backs this; UI must not offer edit/receive controls on an already-received PO, only a read-only line-item view).

### Create / auto-draft flow (single form, two entry paths — satisfies PO-01 and PO-02 together)
- "New Purchase Order" opens a `Dialog` (`max-w-4xl`, mirrors `ReceiveShipmentForm`'s dialog sizing — this form has the same line-item-grid shape).
- Manager picks a supplier first (plain `<select>`, required before anything else is enabled — mirrors `ReceiveShipmentForm`'s supplier-first ordering).
- Once a supplier is selected, a secondary button **"Suggest reorder from low stock"** becomes enabled (disabled with no supplier selected — enforced client-side, not just visually greyed). Clicking it runs the `suggest-reorder` query for that supplier and **replaces** the current line-item list with the suggested lines (each editable afterward) — a single confirmable action, not silent/automatic (satisfies PO-02's "in one action... then edit line items before saving," and avoids PROJECT.md's auto-PO-generation prohibition because nothing is saved until the manager reviews and clicks "Save Draft").
  - If the manager has already manually added lines before clicking "Suggest reorder," show a lightweight native `window.confirm`-free in-app warning is **not** required — instead, disable the suggest button once any line has been manually added/edited, to avoid a silent overwrite. (Simplest correct behavior: "Suggest reorder" only works on an empty line list; once lines exist — whether from suggestion or manual add — the button is disabled/hidden. Manager can still add more lines manually after suggesting.)
- Each suggested line pre-fills: product, quantity (D-07/D-08 formula — already computed by the `suggest-reorder` query, not recomputed in the UI), and cost (D-05/D-06: `inventory.costPrice`, defaulting to 0 with no blocking validation when null — identical to `ReceiveShipmentForm`'s existing cost-default behavior).
- Manual line-add ("Add Line" button) and per-line remove (`×`) behave identically to `ReceiveShipmentForm` — same grid layout (product/qty/cost, no expiry field here since PO creation never touches `inventory`/expiry per D-03), same disabled-submit guard (`!supplierId || lines.length === 0 || lines.some(line => !line.productId || line.quantity <= 0)`).
- **No expiry field on PO line items** (unlike `ReceiveShipmentForm`) — expiry is only meaningful at receive time, which still goes through the existing `receive_shipment` form/flow. Do not add an expiry input to the PO create form; it would be dead data never read back at receive time.
- "Save Draft" inserts `purchase_orders` + `purchase_order_items` via plain RLS-gated mutation (D-03) — no RPC. Closes dialog, shows success toast, list refreshes via TanStack Query invalidation (mirrors `SupplierForm`'s `onSuccess` → `close()` pattern).

### Receive flow (thin wrapper around existing receive-shipment UX)

**Primary visual anchor:** on the PO draft detail view, the "Receive Shipment" button is the single accent-colored focal point (same accent reservation as the list's "New Purchase Order" CTA) — it draws the eye above the read-only line-item table, signaling the one action available on a draft PO's detail screen.

- From the PO list, clicking a `draft`-status row opens a **detail view** (reuse the same `Dialog` shape, or a dedicated `PurchaseOrderDetailPanel` — either is acceptable; the requirement is read/edit access to the line items plus a "Receive Shipment" CTA, not a specific container).
- "Receive Shipment" on a draft PO's detail view opens the **existing `ReceiveShipmentForm`**, pre-filled with the PO's supplier and line items (product/quantity/cost pre-populated, editable — a manager may adjust actual-received quantities/costs/expiry before confirming, since real deliveries can differ slightly from what was ordered) and carrying `poId` through to `useReceiveShipment`. **Do not build a second receive form** — this is RESEARCH.md's explicit "thin wrapper" recommendation and directly enforces D-04. The only addition to `ReceiveShipmentForm` is an optional `poId`/pre-fill prop; its visual layout, field set, and validation rules are otherwise 100% unchanged.
- On successful receive, the extended `receive_shipment` RPC atomically updates stock/cost/expiry **and** sets `purchase_orders.status = 'received'` (D-04) — the UI does not issue a second status-update call. List/detail views refetch and show `received` immediately after the mutation resolves.

### RBAC / route guard (enforces D-01/D-02)
- `PurchaseOrdersRoute` (new, mirrors `ReportsRoute`) wraps the entire `/purchase-orders` route — a cashier navigating there directly is redirected to `/home`, not shown a partial/greyed page.
- `purchase_orders`/`purchase_order_items` RLS uses `FOR ALL` (not a separate open `SELECT` policy) gated to `manage_products`, per RESEARCH.md Pitfall 2 — the UI guard is UX-only; RLS is the real boundary and must not rely on the client alone.
- No permission-conditional rendering within the page (no `<ProtectedAction>` wrapping individual buttons) — the whole route is manager+ or nothing, matching D-02 exactly and the existing Suppliers-page pattern of "the page itself is manager-gated," not per-control gating.

## List Contract (`PurchaseOrderListPanel`)

**Primary visual anchor:** on the PO list screen, the "New Purchase Order" button (top-right of the page header, `POSButton` default/accent variant) is the single focal point — it is the only accent-colored element above the fold, drawing the eye before the table itself.

- **Component:** `DataTable` (existing `src/shared/ui/DataTable.tsx`, TanStack-Table-backed) — not a hand-rolled `<ul>` like `SupplierListPanel` — because this list has multiple sortable/scannable columns (status, date, total), which is exactly `DataTable`'s existing use case (already used elsewhere in the app for tabular entity lists) vs. `SupplierListPanel`'s single-name-per-row shape.
- **Columns:** Supplier name, Status (`StatusBadge` `po_draft`/`po_received`), Line item count, Total cost (`MoneyDisplay`, sum of `quantity × costPrice` across lines — computed client-side or via a view, not stored redundantly), Created date, row-level actions (Delete — draft only, via `×`/trash icon `POSButton variant="destructive"`). **Accessible label required:** the icon-only delete button has no visible text, so it must carry `aria-label={t('wAdmin:purchaseOrderListPanel.delete')}` (reuses the same "Delete" copy key already declared in the Copywriting Contract) — mirrors the existing icon-only-button accessibility pattern already used elsewhere in this codebase (e.g. `SupplierListPanel`'s row actions).
- **Row click:** opens the detail view (draft → editable + Receive CTA; received → read-only).
- **Sorting/filtering:** `DataTable`'s built-in `searchable` prop (search by supplier name) is sufficient — no new filter UI needed. An optional Draft/Received `tabs.tsx` filter above the table is a nice-to-have (existing `tabs.tsx` component available) but not required by PO-01..03's success criteria; the executor may add it if time allows, default view shows all statuses.
- **Loading state:** `TableRowSkeleton` (existing component, already used by `SupplierListPanel`) — 3-4 skeleton rows matching this table's column count.
- **Empty state:** `EmptyState` (existing component) with the copy specified above, action button = "New Purchase Order."
