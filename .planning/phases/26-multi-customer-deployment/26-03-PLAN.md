<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator's local `gh` session ↔ GitHub API | `onboard-customer.ps1` runs with whatever scopes the operator's own already-authenticated `gh` CLI session carries — the script embeds no credentials of its own. |
| `-CustomerMirrorPat` parameter ↔ process listing / shell history | A PAT value passed as a plain string argument would be visible in shell history and `Get-Process`-level command-line inspection on a shared build machine. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-26-07 | Elevation of Privilege | `onboard-customer.ps1` requires an `admin:org`/`repo`-scoped `gh` session to create repos/Environments | low | accept | The script uses the operator's own pre-authenticated `gh` CLI session — no new credential is embedded or escalated; this matches every existing `scripts/*.ps1` in this repo (`generate-build-cert.ps1`, `deploy-remote-backend.ps1`), none of which carry their own service credentials. |
| T-26-08 | Tampering | `$CustomerName`/`$SupabaseProjectRef` parameters interpolated into `gh repo create`/`gh api` calls | high | mitigate | The same `^[a-z0-9-]+$` allow-list validation from Plan 26-02's workflow-side gate is applied here at parameter-validation time, before any `gh`/`git` command executes. |
| T-26-09 | Information Disclosure | `$CustomerMirrorPat` appearing in shell history or a process listing | high | mitigate | Parameter is typed `[System.Security.SecureString]`, decoded to plaintext only in-memory immediately before `gh secret set --env ... CUSTOMER_MIRROR_PAT` reads it via stdin, and the local plaintext variable is nulled out immediately after — never passed as a `-b`/`--body` command-line token. |
