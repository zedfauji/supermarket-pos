# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds no new screens or layouts. It adds exactly two visual/interaction surfaces to the existing checkout UI: (1) a non-blocking `sonner` action-toast that gates add-to-cart for a flagged product (zero-price or low-stock), fired identically from the barcode-scan path and the manual-search path (D-04/D-05), and (2) one new text line (barcode) on the existing `ProductCard` tile (D-03/VER-02). No new dialogs, pages, or components are introduced.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between barcode icon (if used) and barcode text on `ProductCard` |
| sm | 8px | Gap between the new barcode line and the existing name/price lines on `ProductCard` (matches existing `gap-2` on the card's flex column) |
| md | 16px | `ProductCard` tile padding (unchanged, `p-4`) |
| lg | 24px | Not used by this phase's new elements |
| xl | 32px | Not used by this phase's new elements |

**Exceptions (touch-target minimums — must override library defaults):**

- This POS runs on a touchscreen POS terminal; every interactive element in this codebase follows a 44/56/72px minimum touch-target convention (`POSButton`'s `touchSize` variants: `default` 44px, `large` 56px, `xl` 72px). `ProductCard` already uses `touchSize="large"` (56px min-height) — **unchanged by this phase**, the tile itself is not resized to fit the new barcode line; verify the added line does not push the tile's *interactive* height calculation below 56px (it won't — the line only adds to a `flex-col` stack whose container height is already `min-h-[120px]`).
- **`sonner`'s default `[data-button]` CSS is `height: 24px`** [VERIFIED: `node_modules/sonner/dist/styles.css:181-199`] — well under this project's 44px minimum. The Confirm/Cancel toast action buttons (D-04) **must** override this via `action.actionButtonStyle` / `cancel.actionButtonStyle` (sonner's per-toast style prop) setting `minHeight: '44px'`, or a scoped CSS override targeting `[data-sonner-toast] [data-button]`. Do not ship the toast with sonner's 24px default — that is the one genuine touch-target gap this phase introduces and must close before it's considered done.

**New element specifics:**
- `ProductCard` barcode line: `text-xs text-muted-foreground` — matches the existing category-label line's exact classes (`<span className="text-xs text-muted-foreground">`) directly above it, so the two metadata lines read as one visual group. `font-mono` for the barcode digits themselves (matches `MoneyDisplay`'s existing `font-mono tabular-nums` convention for numeric/code data), plain `text-xs text-muted-foreground` for any label text.
- Toast title (product name + flag reason): sonner's default title styling (`text-sm font-medium`, richColors-tinted) — no custom override needed.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--background)` / `var(--foreground)` | Unchanged — checkout page background, this phase adds no new surfaces |
| Secondary (30%) | `var(--card)` | `ProductCard` tile background (unchanged) |
| Accent (10%) | `var(--pos-warning)` (amber, `oklch(0.62 0.17 55)` light / `oklch(0.76 0.17 55)` dark) | **Low-stock** confirmation toast only — fire via `toast.warning(...)`, which activates sonner's built-in `richColors` amber treatment. Matches the existing amber low-stock convention already established in `InventoryPagePanel.tsx` (`border-l-pos-warning`, `bg-pos-warning/10`) — do not invent a new low-stock color. |
| Destructive | `var(--destructive)` (sonner's built-in `richColors` red, via `toast.error(...)`) | **Zero-price** confirmation toast only — a $0 sale is a financial-risk confirmation, styled with sonner's error/red treatment for visual parity with how the app already flags financial-risk states (`MoneyDisplay`'s `text-destructive` for negative amounts). |

Accent reserved for: the low-stock confirmation toast's background/border tint (via `toast.warning()`), nothing else in this phase. Destructive reserved for: the zero-price confirmation toast's background/border tint (via `toast.error()`), nothing else in this phase. **Do not** add a persistent amber/red badge or border to `ProductCard` itself for flagged products — D-03 scopes the card change to the barcode line only; the risk signal lives entirely in the toast, fired at the moment of selection, not as a standing visual state on the tile (a standing badge would contradict D-04's "non-blocking, only-when-flagged" design and risk drifting toward the explicitly-rejected "confirmation on every scanned item" pattern from REQUIREMENTS.md's Out of Scope table).

## Copywriting Contract

**Namespace decision (resolves an open question RESEARCH.md left to the planner):** RESEARCH.md's recommended architecture puts the shared confirm logic in `entities/product/model/useConfirmRiskyAdd.ts` (entities layer, importable by both the `features/scan-barcode-to-cart` feature and the `widgets/CheckoutPanel` widget — see RESEARCH.md's FSD-boundary finding). Per this project's i18n namespace scheme (`entities` = "domain model hooks + `ui/` cards/rows"), **all confirmation-toast copy and the new barcode-line copy live under the `entities` namespace**, not split across `featOrders`/`wPanels` — one copy source for one shared hook, consumed identically by both call sites. New keys: `entities:productRiskConfirm.*` and `entities:productCard.barcodeLabel`.

| Element | Copy |
|---------|------|
| Toast: zero-price title | `entities:productRiskConfirm.zeroPriceTitle` = "{{name}} is priced at $0" |
| Toast: zero-price body | `entities:productRiskConfirm.zeroPriceBody` = "Add it to the cart at $0?" |
| Toast: low-stock title | `entities:productRiskConfirm.lowStockTitle` = "Only {{count}} left of {{name}}" (react-i18next `_plural`-aware: `count === 1` → "Only 1 left of {{name}}") |
| Toast: low-stock body | `entities:productRiskConfirm.lowStockBody` = "Add it to the cart anyway?" |
| Toast: Confirm action (both flags) | `entities:productRiskConfirm.confirm` = "Add anyway" |
| Toast: Cancel action (both flags) | `entities:productRiskConfirm.cancel` = "Cancel" |
| `ProductCard` barcode line | `entities:productCard.barcodeLabel` = "Barcode: {{code}}" |
| Primary CTA (this phase's one new user action) | "Add anyway" — the toast's Confirm button; this is the only new call-to-action this phase introduces (there is no new page-level primary CTA) |
| Empty state | N/A — this phase adds no new list/collection view; `ProductGrid`'s existing "no results" empty state is unchanged and out of scope here |
| Error state | N/A — this phase adds no new error state; `scanBarcodeToCart.productNotFound` (existing `toast.error`) is unchanged. The zero-price/low-stock toasts are **confirmations requiring a decision**, not errors, even though the zero-price toast borrows sonner's error/red color treatment for visual weight (see Color section) |
| Destructive confirmation | Zero-price confirm: "{{name}} is priced at $0 — Add anyway / Cancel". This is the closest this phase has to a "destructive" action (confirming adds an item at $0, a real revenue-loss risk) — no separate `ConfirmDialog`/manager-PIN gate is introduced (D-06 explicitly rejects a price-override step; the toast IS the confirmation) |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 6 covered, 1 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| long-text | Toast title (product name) | ✅ covered | Sonner's default title styling wraps (`line-height: 1.5`, no `white-space: nowrap`) — a long product name wraps to a second line inside the toast rather than being clipped or overflowing the toast card; no truncation needed since the toast has no fixed single-line height constraint |
| overflow | `ProductCard` barcode line | ✅ covered | Apply the same `truncate` class the card already uses on its product-name `<h3>` (`w-full truncate`) to the new barcode line, so a barcode that doesn't fit the tile's fixed width ellipsizes rather than wrapping/overflowing the 120px-min-height tile |
| zero-one-many | Low-stock toast quantity (`{{count}}`) | ✅ covered | Use react-i18next's built-in plural key resolution (`lowStockTitle` / `lowStockTitle_other`, or an ICU `{{count, plural, ...}}` block per this project's existing i18next config) so `count === 1` ("Only 1 left") reads correctly, not "Only 1 lefts" or an awkward singular/plural mismatch |
| partial | Weighted (`soldByWeight`) flagged product | ✅ covered | Per RESEARCH.md's Pitfall 3 / Open Question 1 recommendation: the confirm toast gates **before** `WeightEntryDialog` opens (same trigger point as the unweighted `addItem` gate), not after weight entry. Visually this means a flagged weighted product shows the exact same toast as a flagged unweighted product; `WeightEntryDialog` never opens until Confirm is pressed |
| many (concurrent toasts) | Multiple pending confirmation toasts (rapid re-scan while one is pending) | ✅ covered | No custom queue/dedup UI — rely on `sonner`'s native toast stacking (each `toast()` call gets its own id and stacks visually per `Toaster`'s existing config); CONTEXT.md's Claude's Discretion explicitly defers to this default |
| loading | N/A — flag check | ✅ covered | The risk-flag check (`getProductRiskFlag`) is a synchronous pure-function read over already-fetched/cached `Product` data (RESEARCH.md Architecture Patterns) — no network round-trip at confirm-time, so no loading/spinner state is needed on the toast itself |
| overflow | Toast stack exceeding visible viewport height (many pending toasts) | 🧪 backstop | Sonner's own default max-visible-toast / collapse behavior is assumed sufficient for a 1-2 terminal single-store POS (low realistic concurrency of pending confirmations); no explicit design decision was made to override sonner's defaults here — held out as a visual-regression backstop rather than a covered truth |
