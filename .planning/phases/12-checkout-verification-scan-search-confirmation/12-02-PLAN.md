<objective>
Plan 12-01 built the shared risk-gate mechanism (`getProductRiskFlag`, `useConfirmRiskyAdd`) and wired it into the barcode-scan path. This plan reuses that exact same mechanism for the manual-search path and satisfies VER-02 by adding a barcode line to `ProductCard`.

**Correction to RESEARCH.md/12-PATTERNS.md's assumed wiring point:** both docs describe inserting the risk-gate into `CheckoutPanel.tsx`'s `onSelect={product => addItem(product, [])}` callback. Direct inspection of the current code shows this is wrong for the weighted branch: `ProductGrid.tsx` already decides `soldByWeight` internally, inside the `onSelect` prop it passes down to `ProductCard` (`if (selectedProduct.soldByWeight) weightEntry.openFor(selectedProduct); else onSelect(selectedProduct);`) — `CheckoutPanel`'s own `onSelect` prop is only ever invoked for the non-weighted branch. Gating only in `CheckoutPanel.tsx` would silently skip the confirm toast for every flagged, `soldByWeight` product selected via search (opening `WeightEntryDialog` unguarded), which would violate the same "partial: soldByWeight" UI consideration 12-01 already satisfied on the scan path. This plan therefore gates inside `ProductGrid.tsx`'s own `onSelect` callback (the one place both branches funnel through) and does **not** touch `CheckoutPanel.tsx` at all.

Purpose: give the cashier the same "wrong-row click is caught before commit" safety net (VER-02) and the same risk confirmation (VER-01) regardless of whether they reached the product by scanning or by tapping a search result.
Output: `ProductCard.tsx` renders a barcode line; `ProductGrid.tsx`'s tile-select callback gates through the shared `useConfirmRiskyAdd` hook; `e2e/51-barcode-scan-search.spec.ts` gains search-path coverage.
</objective>
