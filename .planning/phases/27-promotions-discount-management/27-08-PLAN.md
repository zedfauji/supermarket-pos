<objective>
Fix gap G-27-13 (blocker): a cashier who gets a real manager to type their PIN into ManagerPinDialog
during checkout still has the sale rejected server-side with FORBIDDEN/DISCOUNT_REQUIRES_MANAGER,
because `process_direct_sale_atomic`'s manager-override re-check is keyed off the CURRENTLY
LOGGED-IN staff's own id (`p_staff_id`, resolved from the session JWT) — never the staff whose PIN
was actually entered in the dialog. `ManagerPinDialog.onSuccess()` is zero-argument, so no caller can
even know which staff matched.

Root cause is documented in full in
`.planning/debug/adhoc-discount-manager-pin-rejected-after-entry.md`. This plan closes it on the
direct-sale (CheckoutPanel) path — the path the reported error actually comes from. The same defect
on the reopened-tab (PaymentPane) path is closed by the follow-on plan 27-09.

**Scope decision (document per gap instructions):** `ManagerPinDialog`'s `onSuccess` contract is
widened GLOBALLY (Task 1) — this is free and zero-risk, since TypeScript always allows a callback
prop typed `(staff: Staff) => void` to be satisfied by an existing `() => {...}` consumer (fewer
declared params is always assignable). All 14 existing consumers keep compiling with zero code
changes. However, the SERVER-SIDE authorization fix (threading the matched staff's PIN through to an
RPC's own independent re-verification) is applied NARROWLY — only to `process_direct_sale_atomic`
(this plan) and `process_payment_atomic`/`process_split_payment_atomic` (plan 27-09). The other 12
`ManagerPinDialog` consumers (`process_refund`, `reopen_tab_rpc`, `edit_paid_tab_rpc`, `close_tab`,
etc.) share the exact same structural defect but are OUT OF SCOPE for this phase's gap closure — file
a follow-up todo in STATE.md's Pending Todos (Task 2) rather than touching those RPCs here, since each
has its own call shape and blast radius that deserves its own review, not a rushed bundle fix.

**Why PIN-based re-verification, not staff-id-based:** the client already fetches every staff
member's plaintext PIN via `useStaffList()` (an existing, accepted property of this app's security
model — see `IdleLockOverlay.tsx`'s doc comment). If the server instead trusted a client-supplied
`p_manager_staff_id` directly, a tampered client (dev tools, a modified build, a raw PostgREST call)
could claim ANY manager's UUID — enumerable from that same staff list — as the authorizing identity
without ever knowing their PIN, which is a strictly WORSE elevation-of-privilege hole than the bug
being fixed (see `<threat_model>` T-27-10). Instead, the server independently re-derives the
authorizing staff from the raw PIN string itself (`profiles.pin = p_manager_pin`), mirroring exactly
the lookup the client already performs — the server's version just can't be tampered with by changing
a request body field.

Purpose: Restore the actual value of the manager-PIN-override UX (a cashier stays logged in; a
manager authorizes in place) for the one flow (ad-hoc discount / below-cost override at direct-sale
checkout) this phase shipped.
Output: Widened `ManagerPinDialog` contract, PIN threaded end-to-end through the direct-sale payment
path, a real cashier + distinct-manager E2E proof.
</objective>
