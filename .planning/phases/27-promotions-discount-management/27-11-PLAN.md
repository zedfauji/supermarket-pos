<objective>
Build the backend data model for Part B of gap G-27-8 (the promotion dialog redesign) — the genuine
scope expansion beyond what Phase 27 originally shipped: a promotion's scope becomes 0..N products AND
0..N categories (including a valid "no restriction" / store-wide promotion with zero targets), plus
NEW recurring day-of-week and time-of-day windows. This is new requirement coverage on top of PROMO-01
(which only ever specified "a product, a category, or a subcategory" — a single target), not a bug fix.

This is the tracer for the whole Part B effort: it proves the new data model end-to-end at the
checkout-pricing layer (a multi-product, multi-category, recurring-window promotion can be created via
direct RPC calls and correctly prices a real checkout) BEFORE any UI exists to create one through the
app — the wizard screen (plan 27-14) is pure UI on top of what this plan proves works.

**Backward-compatible design (deliberate, to avoid destabilizing already-shipped PROMO-01..09):**
Legacy `product_id`/`category_id` columns and the still-live `PromotionFormDialog.tsx` are NOT removed
or migrated away by this plan — they keep working exactly as today as a "single-target fast path". New
multi-target/store-wide/recurring promotions are represented ONLY via the new junction tables and
recurrence columns, left NULL/empty on the legacy columns. The checkout-pricing matching query (Task 3)
checks BOTH representations. `domain.ts`'s `PromotionSchema` gains new fields additively — nothing is
removed, so no other file in this codebase needs to change to keep compiling. The wizard (plan 27-14)
is what eventually retires the legacy write path by deleting `PromotionFormDialog.tsx`; a later cleanup
(dropping the now-unused legacy columns) is explicitly deferred, not this plan's concern.

**Why this plan depends on 27-08:** `process_direct_sale_atomic` was already `CREATE OR REPLACE`'d by
plan 27-08 (adding `p_manager_pin`-based re-verification). Task 3's own `CREATE OR REPLACE` of the same
function must start from THAT already-modified body, not the pre-27-08 version, or it would silently
revert 27-08's fix.

Purpose: give the wizard (plan 27-14) real backend capability to save against, and prove the pricing
engine correctly resolves the new scope/recurrence model before any UI depends on it.
Output: junction tables + recurrence columns, an atomic `save_promotion_with_targets` RPC, an updated
checkout-time candidate-matching query, and an additive `domain.ts` type update.
</objective>
