<objective>
Extend `evaluateBestPromotion` — the pure, already-unit-tested pricing function backing the live
cart-display discount preview (PROMO-03) and the payment screen's "Apply Promotion" selector (PROMO-05)
— to understand the new multi-target scope and recurrence-window fields plan 27-11 added to
`domain.ts`'s `Promotion` type. This is a textbook TDD candidate: `promotion-pricing.test.ts` already
exists with clear `input -> expected output` assertions; this plan extends that same file with new
cases for the new matching rules, then implements them.

A genuinely new small helper (`src/shared/lib/store-time.ts`) is needed to answer "what day-of-week and
time-of-day is it right now, in the store's configured timezone" from a plain JS `Date` — there is no
existing reusable timezone-conversion helper anywhere in `shared/lib` (confirmed by search). This
mirrors (never literally shares — this file's own doc comment already establishes that convention) the
Postgres-side `now() AT TIME ZONE v_timezone` logic 27-11 wrote into `process_direct_sale_atomic`.

Purpose: keep the client-side cart-display preview and the server-side checkout authority in sync for
the new scope/recurrence rules — a mismatch here would mean the cart shows a discount the server then
rejects (or vice versa), a UX regression this codebase has explicitly guarded against before (PROMO-03
already documents this class of risk).
Output: `evaluateBestPromotion` correctly matches multi-target/store-wide/recurrence-windowed
promotions; a new `getStoreLocalDayAndTime` helper.
</objective>

  <name>evaluateBestPromotion matches multi-target scope and recurrence windows</name>
  <files>src/entities/promotion/model/promotion-pricing.ts, src/entities/promotion/model/promotion-pricing.test.ts, src/shared/lib/store-time.ts, src/shared/lib/store-time.test.ts</files>
  <behavior>
    Cases to add to promotion-pricing.test.ts (existing file, existing PRODUCT/NOW fixtures — extend,
    do not replace):
    - A promotion with `productIds: [PRODUCT.productId, otherProductId]`, `categoryIds: []` matches
      PRODUCT. A promotion with `productIds: [otherProductId]` only does not match PRODUCT.
    - A promotion with `categoryIds: [PRODUCT.categoryId]`, `productIds: []` matches PRODUCT via
      category.
    - A promotion with `productIds: []`, `categoryIds: []` (store-wide) matches PRODUCT.
    - A promotion with legacy `scopeType: 'product'`, `productId: PRODUCT.productId` (empty
      productIds/categoryIds arrays) still matches — proves the extension doesn't regress PROMO-01's
      original single-target behavior.
    - A promotion with `recurrenceDaysOfWeek: [2]` (Tuesday) evaluated with a `now` that falls on a
      Monday does not match, even though productIds/date-range would otherwise qualify it. The same
      promotion evaluated with a `now` that falls on a Tuesday does match.
    - A promotion with `recurrenceTimeStart: '16:00'`, `recurrenceTimeEnd: '18:00'` evaluated with a
      store-local time of 17:00 matches; evaluated at 19:00 does not.
    - `recurrenceDaysOfWeek: null` and `recurrenceTimeStart/End: null` (the common case — no
      recurrence restriction) behaves identically to before this plan for every existing test case.

    New store-time.test.ts cases (pure function, no Date-mocking framework needed beyond constructing
    explicit `Date` instances and an IANA timezone string):
    - `getStoreLocalDayAndTime(new Date('2026-09-08T22:30:00Z'), 'America/Mexico_City')` (UTC-6, no
      DST at that date) returns ISO day-of-week 2 (Tuesday, since 2026-09-08 16:30 local is still
      Tuesday) and a time-of-day of '16:30'.
    - A UTC instant that crosses the store-local midnight boundary in either direction resolves to the
      correct LOCAL day-of-week, not the UTC day-of-week (e.g. a UTC instant that is Wednesday 02:00 UTC
      resolves to Tuesday 20:00 in America/Mexico_City — the day-of-week the recurrence check must use
      is Tuesday, not Wednesday).
  </behavior>
  <implementation>
    Create `src/shared/lib/store-time.ts` exporting `getStoreLocalDayAndTime(now: Date, timezone:
    string): { isoDayOfWeek: number; timeOfDay: string }` — implement via
    `Intl.DateTimeFormat('en-US', { timeZone: timezone, weekday: 'short', hour: '2-digit', minute:
    '2-digit', hourCycle: 'h23' }).formatToParts(now)`, mapping the `weekday` part ('Mon'..'Sun') to
    ISO day-of-week 1-7 and combining `hour`/`minute` parts into an `'HH:MM'` string. Zero new
    dependencies — `Intl` is a JS/browser built-in already used elsewhere in this codebase's `brain.ts`.

    In `promotion-pricing.ts`'s `evaluateBestPromotion`, replace the `matchesScope` line (currently
    `(promo.scopeType === 'product' && promo.productId === product.productId) || (promo.scopeType ===
    'category' && promo.categoryId === product.categoryId)`) with a check against BOTH the new array
    fields and the legacy singular fields: `const scopedViaArrays = promo.productIds.includes(
    product.productId) || promo.categoryIds.includes(product.categoryId); const scopedViaLegacy =
    (promo.productId != null && promo.productId === product.productId) || (promo.categoryId != null &&
    promo.categoryId === product.categoryId); const isStoreWide = promo.productIds.length === 0 &&
    promo.categoryIds.length === 0 && promo.productId == null && promo.categoryId == null; const
    matchesScope = scopedViaArrays || scopedViaLegacy || isStoreWide;`. Add a recurrence guard evaluated
    alongside the existing `now < promo.startsAt || now > promo.endsAt` date check: accept a NEW
    required parameter `timezone: string` (thread it from every call site — `PaymentForm.tsx`'s
    `effectiveItems` useMemo and the add-to-cart call sites read timezone from `useSettings()`'s general
    settings, already available wherever `evaluateBestPromotion` is currently called), compute
    `const { isoDayOfWeek, timeOfDay } = getStoreLocalDayAndTime(now, timezone)`, and skip a candidate
    when `promo.recurrenceDaysOfWeek != null && !promo.recurrenceDaysOfWeek.includes(isoDayOfWeek)` or
    when `promo.recurrenceTimeStart != null && !(timeOfDay >= promo.recurrenceTimeStart && timeOfDay <=
    promo.recurrenceTimeEnd)` (string comparison on zero-padded 'HH:MM' is lexicographically correct for
    same-day ranges — this codebase's `DateRangePicker` already relies on the equivalent property for
    date strings).
  </implementation>
