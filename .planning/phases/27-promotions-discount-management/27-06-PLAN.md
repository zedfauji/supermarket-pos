<objective>
Close PROMO-08: a discount computed while offline must never be silently trusted or silently
re-priced once the terminal reconnects — if the promotion that produced it changed or disappeared in
the meantime, flag the affected cart line for the cashier to review before checkout proceeds.

Purpose: direct-sale checkout already refuses to submit while offline (`useCheckoutSale`'s `submit()`
hard-errors on `!isOnline()` — there is no queued-replay path for a direct sale, unlike the
legacy tab-based offline queue). The actual offline risk is therefore narrower than a generic
"offline queue replay" problem: a cashier can add items to the cart while offline (a pure local
action, no network needed), see a promotion-discounted price computed from stale cached data, then
reconnect and attempt to check out — this plan makes that reconnect moment safe.
Output: cart-line promotion-conflict detection on reconnect, a blocking review affordance, and the
PROMO-08 E2E proof.

Flagged assumption (specless-probe-fallback, PROMO-08's edge item was categorized "unclassified" and
is intentionally NOT auto-resolved): this plan's conflict detection covers cart lines whose discount
came from a real `promotions` row (`promotionId` non-null). It does NOT re-flag a line whose discount
came only from the expiry-proximity auto-trigger (`promotionId` null, config-driven), because that
trigger's config (`near_expiry.thresholdDays`/`discountPercent`) changes far less often than a
promotion row's active state — if the store finds this insufficient in practice, extending
conflict-detection to the expiry-trigger path is a small follow-up, not a blocker for this phase.
</objective>
