<objective>
Close gap G-27-13's secondary finding: unlike `process_direct_sale_atomic` (fixed in plan 27-08),
`process_payment_atomic`/`process_split_payment_atomic` — the RPCs behind the reopened-tab
(`PaymentPane`) payment screen — have no manager-override authorization check at all today, and
`process-payment`'s edge function doesn't even forward the discount fields (Zod silently strips them).
Worse, `process-split-payment`'s edge function schema uses stale bar-pos-era enum values
(`discountScope: 'tab'|'item'`, `discountType: 'percentage'|'fixed'`) that don't match what the client
actually sends (`'all'`, `'percent'|'fixed'`) — any split-payment discount request fails Zod validation
before it ever reaches the RPC.

This plan gives `process_payment_atomic`/`process_split_payment_atomic` the SAME PIN-based
re-verification pattern plan 27-08 gave `process_direct_sale_atomic`, wires the two edge functions to
actually forward the discount+manager fields, and updates `process_direct_sale_atomic`'s own internal
delegation to those two functions so its already-approved direct sales are not newly rejected by the
inner check this plan adds.

Purpose: complete the fix so the ad-hoc-discount + manager-PIN flow works identically on BOTH payment
screens (direct-sale checkout and reopened-tab), closing the "silent underpayment" class of bug the
debug session flagged (a discount recorded with zero server-side authorization) alongside the
originally-reported rejection bug.
Output: `process_payment_atomic`/`process_split_payment_atomic` gain manager-override authorization;
both edge functions forward the fields correctly; a real PaymentPane E2E proof.
</objective>
