## 1. System Classification

**System Type:** Conversational assistant with bounded tool proposals

**Description:**
An optional, separately installed, loopback-only local assistant lets authenticated cashiers, managers, and administrators propose POS operations in English or Spanish. The local model is an untrusted parser: a TypeScript gateway validates one allow-listed proposal, resolves the live session, re-applies existing RBAC/RLS and operation-specific approval, then uses the normal authorised POS path. Checkout stays available if the assistant is absent, slow, or rejected.

**Critical Failure Modes:**
1. A model proposal performs or authorizes an operation beyond the current user's permission, or bypasses the existing approval/PIN flow.
2. An injected, malformed, stale, replayed, or over-broad request reaches a POS write path, remote/local Supabase credential, SQL, shell, filesystem, or arbitrary network capability.
3. The assistant reports or mutates stale/incorrect data, including claiming offline data is available when it is not.
4. Inference starves checkout of CPU/RAM, or a sidecar failure degrades ordinary POS use.
5. An action, approval, outcome, or model/runtime provenance is missing from the immutable audit trail.

## 1b. Domain Context

**Industry Vertical:** Retail / supermarket point of sale

**User Population:** Cashiers completing live sales, managers supervising inventory, reporting and
exceptions, and administrators maintaining staff/settings on shared, resource-constrained store PCs.

**Stakes Level:** High — the assistant cannot decide authority, but an approved proposal can affect
live inventory, catalog, operational configuration, staff data, and the business decisions made from
reports. Payment-account data must never enter the assistant path.

**Output Consequence:** Gateway-rendered reads guide store actions; a confirmed mutation reaches the
same live server-authoritative POS path as the normal UI. Incorrect, unauthorized, duplicated, or
untraceable output can cause loss, fraud opportunity, reconciliation errors, or exposure of staff/
customer data.

### What Domain Experts Evaluate Against

| Dimension | Good (operator accepts) | Bad (operator flags) | Stakes | Source |
|---|---|---|---|---|
| Role-respecting operation | The same logged-in user and the same live permission/server guard that the UI uses permit the exact action; required manager PIN identity is re-verified. | A cashier can stage or confirm a manager/admin operation, or the model's claimed role is trusted. | Critical | Existing POS RBAC and manager-PIN design; NIST AI RMF accountability/resilience principles. |
| Preview fidelity and explicit approval | Before a write, the named entity, current value/version, exact diff, approval actor and consequence are shown in the user's language; one explicit tap authorizes that exact version only. | A vague “updated product” card, a changed target/value after preview, or a chat utterance such as “yes” executes an action. | Critical | Retail manager/cashier operating practice; existing POS confirmation pattern. |
| Authoritative, reconcilable result | A report or completed action is derived from the configured live Supabase target and bounded by its server rules; the result names its date/range/status and durable audit trail. | The assistant fills gaps with model prose, treats local inference as local business data, or cannot explain which committed action occurred. | High | Retail reconciliation practice; NIST AI RMF valid/reliable and accountable/transparent characteristics. |
| Checkout-first availability | A slow, missing, or malformed assistant request fails closed with a concise bilingual status while scanning, cart, payment, and printing remain responsive. | CPU/RAM contention delays checkout, an assistant crash blocks the POS, or a timeout silently retries an operation. | Critical | Store operations require checkout continuity; existing local-hardware performance research. |
| Bilingual safe assistance | English and Spanish requests map to the same permitted proposal or the same clear localized refusal; ambiguous names/dates ask the operator to choose. | Spanish is coerced to a different operation, an invented translation hides a denial, or an ambiguous product/staff target is guessed. | High | Bilingual store user population and safe human-in-the-loop operation. |

### Known Failure Modes in This Domain

1. **Authority laundering:** an assistant's plausible phrasing, stale role, or copied confirmation token
   is mistaken for current authorization and opens a privileged inventory/settings/staff change.
2. **Wrong shelf/item or stale state:** fuzzy product/staff matching, prices displayed in the wrong
   unit/currency, or stale report dates make a real but unintended change look reasonable.
3. **Duplicate or untraceable write:** retry/replay turns one approval into several writes, or an
   audit record lacks actor, terminal, approval, payload version, model/runtime provenance, or outcome.
4. **Checkout denial of service:** long context, unlimited decode, a locally reachable inference
   endpoint, or memory mapping crowds out scanning, payment, printing, or the browser UI.
5. **Data/payment-scope leakage:** prompts, transcripts, model logs, or tool arguments capture staff/
   customer personal data or payment-account/sensitive-authentication data.

### Regulatory / Compliance Context

This is not legal advice. For Mexican private-sector deployments, the current *Ley Federal de
Protección de Datos Personales en Posesión de los Particulares* regulates legitimate, controlled and
informed handling of personal data and defines privacy notices, consent and ARCO rights. The assistant
therefore stores no chat history by default, sends no data to cloud AI, and needs a documented retention/
access policy before any optional audit transcript or customer/staff data is retained. PCI DSS applies
where payment account data is stored, processed, or transmitted; sensitive authentication data must
not be stored after authorization. Keep PAN, CVV/CVC, track data, PIN/PIN blocks and processor secrets
out of the assistant prompt, model, logs, preview, and tool registry; review any payment feature with
the merchant's PCI/compliance owner before it is enabled.

NIST's AI RMF is voluntary guidance, not a legal mandate; it supports the chosen govern–measure–manage
evidence trail and recurring review of high-impact failures.

## 2. Framework Decision

**Selected Framework:** No agent-orchestration framework — direct TypeScript local-model bridge + existing Zod gateway + loopback llama.cpp/GGUF sidecar

**Version:** Zod 4.3.6 (existing); pin llama.cpp and the approved GGUF model only after Phase 29's packaging/performance proof gate

**Rationale:**
This is a bounded conversational router, not an autonomous workflow. A direct TypeScript bridge produces one schema-constrained proposal; the POS gateway remains the only authority for session identity, RBAC/RLS, operation-specific preview/re-authentication, normal authorised execution, and immutable audit. It avoids Python, cloud APIs, a duplicate policy engine, and orchestration/checkpoint overhead on constrained hardware.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph.js 1.x | Defer unless a later release needs proven resumable, user-visible multi-step workflows; graph/checkpoint state is needless for propose → approve → execute. |
| LangChain.js | Defer unless a measured retrieval or heterogeneous integration need exceeds a tiny local-model interface. |
| Python-only/CrewAI/AutoGen/Google ADK | Violates the TypeScript-only and small-footprint constraints. |
| OpenAI/Anthropic SDKs | Violates the local, model-agnostic, no-cloud-AI-API requirement. |
| LlamaIndex | Retrieval-first; V1 does not need RAG. |

**Vendor Lock-In Accepted:** No — llama.cpp/GGUF and the small `LocalModel` adapter remain model-runtime replaceable.

## 3. Framework Quick Reference

The assistant uses no agent SDK. Its only AI dependency is a small `LocalModel` adapter over a
separately installed llama.cpp HTTP server; the POS gateway owns validation and execution.

### Installation and lifecycle

The **optional assistant installer**, not the POS installer, delivers an audited llama.cpp binary
and one approved GGUF model. Its manifest pins both release and SHA-256, verifies the files before
starting, and rejects a complete runtime+model larger than 1 GB. The installer starts a CPU-only
server such as:

```powershell
llama-server --model <approved.gguf> --host 127.0.0.1 --port <configured-loopback-port> `
  --threads <hardware-profile-cap> --prio -1 --ctx-size <bounded-context> --n-predict <bounded-output> --offline
```

`llama.cpp` binds to `127.0.0.1` by default, supports a thread cap, low priority, bounded context
and output, offline mode, and JSON-schema constrained responses. Do not enable its function/tool
runtime, remote model download, media paths, embeddings, or public/LAN binding.

### Core imports

```ts
import { z } from 'zod';

type LocalModel = {
  propose(messages: readonly ChatMessage[], signal: AbortSignal): Promise<unknown>;
};
```

### Entry point pattern

```ts
type ChatMessage = { role: 'system' | 'user'; content: string };
declare const proposalJsonSchema: Record<string, unknown>; // reviewed build artifact from Proposal

const response = await fetch(`${loopbackBaseUrl}/v1/chat/completions`, {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  signal: AbortSignal.timeout(8_000),
  body: JSON.stringify({
    model: configuredModelId,
    temperature: 0,
    max_tokens: 160,
    stream: false,
    messages: boundedPrompt,
    response_format: { type: 'json_schema', schema: proposalJsonSchema },
  }),
});

if (!response.ok) throw new Error('LOCAL_MODEL_UNAVAILABLE');
const body = await response.json() as { choices?: Array<{ message?: { content?: string } }> };
const content = body.choices?.[0]?.message?.content;
let value: unknown;
try { value = typeof content === 'string' ? JSON.parse(content) : undefined; } catch { value = undefined; }
const parsed = Proposal.safeParse(value);
if (!parsed.success) return gateway.refuse('invalid_proposal');
return gateway.stage(parsed.data, currentAuthenticatedSession());
```

The endpoint is OpenAI-compatible only at the local HTTP shape; the POS neither imports an OpenAI
SDK nor sends data to an OpenAI service. `response_format` constrains shape, while the local Zod
parse and gateway checks remain mandatory.

### Key abstractions

| Concept | What it is | Use it for |
|---|---|---|
| `LocalModel` | Tiny `fetch` adapter around the loopback server | Keep llama.cpp and any later local runtime swappable. |
| `Proposal` | Strict discriminated Zod union | Admit exactly one known action or refusal, never free-form tool calls. |
| Tool registry | Gateway-owned mapping from proposal kind to an existing POS feature/RPC | Add one operation only after its server authorization, preview, approval, audit, and tests are proven. |
| Approval record | Durable, single-use, actor/terminal/payload/version-bound proposal | Turn a preview into one authorized execution; never reuse `pendingActions.ts`. |
| Deterministic presenter | i18next-backed renderer of gateway result and refusal codes | Prevent model text from echoing injected input or misrepresenting result data. |

### Common pitfalls

1. **Treating JSON-schema grammar as authorization.** It can shape output, but it cannot prove that a
   tool, ID, date, amount, or role is correct; reject unknown keys, resolve all IDs/current state in
   the gateway, and re-check RBAC/RLS at execution.
2. **Using llama.cpp's tool runtime or passing credentials to the model.** The model needs neither a
   Supabase URL/JWT nor SQL, filesystem, shell, or network access; it emits a proposal only.
3. **Shipping an unbounded server.** Defaults permit unlimited prediction/context and all CPU threads;
   set caps, a short client timeout, low process priority, and unload/disable the assistant under
   memory pressure. Checkout wins every contention decision.
4. **Calling a local endpoint “offline data.”** Local inference does not replicate Supabase. When the
   configured remote or Docker-local Supabase target is unavailable, show the localized
   `data_unavailable` response and perform no operation.
5. **Letting model prose describe results or approvals.** Render approved data, previews, denials, and
   outcomes from gateway-owned typed values and i18n keys, not a second model pass.

### Recommended project structure

```text
src/shared/lib/local-assistant/
  model.ts             # local loopback fetch, timeout, health only
  proposal.ts          # strict Zod contracts and JSON schema export
  gateway.ts           # current-session RBAC, staging, dispatch
  approval.ts          # durable one-time approval binding
  presenter.ts         # i18next response/preview rendering
  tool-registry.ts     # small explicit mapping to existing POS paths
assistant-installer/   # separate build/release, binary/model manifest and hash verification
```

## 4. Implementation Guidance

**Model configuration:** benchmark candidate Q4 GGUF models from the existing research before
approval; do not hard-code a model name in the POS. Use `temperature: 0`, one output only
(`max_tokens: 160`), bounded context, 8-second request timeout, one retry only for a transport error,
and never retry a parsed proposal or an execution. A hardware profile selects the conservative CPU
thread/context cap; on pressure or failed health checks the assistant is unavailable and the POS
continues normally.

**Core pattern:**

1. Accept a length-limited text request after rate limiting and local injection-pattern screening.
2. Send only the fixed policy, language preference, small sanitized conversation window, and no
   credentials or business-result text to the loopback model.
3. Parse one strict proposal. The model can propose `refuse`, a read, or one registered mutation; it
   cannot chain calls or submit a final answer.
4. Gateway independently resolves the current session, role, terminal, live target IDs and current
   record version; it rejects absent/changed/unauthorized values before producing a typed preview.
5. Reads run through the existing authenticated query/RPC with bounded output. Mutations create a
   durable, short-lived, single-use approval bound to actor, authorizing PIN identity when needed,
   terminal, exact payload hash, target version, policy/model/runtime version, and expiry.
6. On the explicit confirm tap, re-check the same session/RBAC/RLS and normal server-side invariant,
   consume the approval atomically, dispatch through the existing feature/RPC/Edge Function, and
   write the immutable intent/approval/outcome audit trail. Localize the typed result in the UI.

**Tool use:** start with an empty registry and expose each already-supported POS operation only through
the same underlying authorization path it uses in the UI. "All POS operations" is a compatibility
goal, not permission to add a generic CRUD/Supabase tool: each registry entry declares its Zod args,
safe preview fields, RBAC action, whether a manager PIN/re-auth is required, its server-authoritative
dispatcher, and audit action. Payments, refunds, voids, RBAC/staff-role changes, backup/restore, audit
modification, SQL, shell, filesystem, and arbitrary networking remain absent until a specific design,
server guard, and adversarial test prove them safe.

**State management:** conversation is UI-local and bounded; never use it for authorization. Approval
state is durable and server-authenticated because the legacy process-local `pendingActions.ts` token
is neither cryptographically strong nor session/payload/terminal bound. The model sidecar persists no
POS session, JWT, query result, approval, or secret. The existing Supabase client configuration remains
the sole selector for remote hosted and Docker-local Supabase deployments.

**Context window strategy:** no RAG or embeddings in this phase. Retain at most the minimal recent
user/assistant intents needed for disambiguation; never include retrieved documents, untrusted product
notes, audit text, database result blobs, credentials, or prior approvals as instructions. Use gateway
lookups only after an allow-listed proposal and return compact typed choices to the UI.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic-equivalent Zod

Pydantic is **N/A**: this is a TypeScript-only product and Zod 4.3.6 is already installed. Export the
same strict schema as JSON Schema for llama.cpp, then independently parse its response with Zod.

```ts
import { z } from 'zod';

const ProductLookup = z.object({ query: z.string().trim().min(1).max(80) }).strict();
const UpdateProduct = z.object({
  id: z.string().uuid(),
  name: z.string().trim().min(1).max(120).optional(),
  priceCents: z.number().int().min(0).max(10_000_000).optional(),
}).strict().refine(value => value.name !== undefined || value.priceCents !== undefined);

export const Proposal = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('refuse'), reason: z.enum(['unsupported', 'unsafe', 'ambiguous']) }).strict(),
  z.object({ kind: z.literal('product.lookup'), args: ProductLookup }).strict(),
  z.object({ kind: z.literal('product.update'), args: UpdateProduct }).strict(),
]);

export function parseProposal(json: string): z.infer<typeof Proposal> | null {
  try {
    const result = Proposal.safeParse(JSON.parse(json));
    return result.success ? result.data : null;
  } catch {
    return null;
  }
}
```

At most one inference retry is allowed for a transport failure before any proposal is parsed. A schema
failure, unknown proposal, invalid range, authorization denial, stale target, or duplicate approval is
recorded as a rejected attempt and returns a local, localized refusal; it is never repaired by a model
retry.

### Async-First Design

Use one cancellable `fetch` per turn with `AbortSignal.timeout`; cancel it when the chat closes, the
session changes, or checkout pressure mode activates. Stream only non-authoritative typing feedback if
it is proven to cost no UI responsiveness; await the complete structured proposal before parsing or
staging. Never stream model tokens into previews, audits, or the DOM as an answer.

### Prompt Engineering Discipline

The fixed system contract lists only the registered proposal schema and says that unrecognized or
ambiguous requests must select `refuse`. User text is data, delimited from policy, capped in size, and
never promoted into system instructions. Use a tiny bilingual few-shot set only for approved proposal
kinds; keep English/Spanish display text in i18next, not in the model. Every request declares a token
and output cap; never let a local model inherit an unlimited default.

### Context Window Management

Keep only the latest bounded dialogue turns needed to resolve intent, discard prior tool/result content
after local presentation, and require the user to choose when an entity match is ambiguous. Do not
summarize state with the model; the authoritative current state is re-fetched by the gateway at stage
and confirm time.

### Cost and Latency Budget

There is no cloud-call cost. The hard budget is a complete external assistant install below 1 GB plus a
measured CPU/RAM envelope on target hardware. The spike's warm workstation latency is evidence only,
not a target. The packaging spike must record cold start, first proposal, repeated EN/ES p95, RSS,
threads/CPU, disk size, and checkout responsiveness on 4-core/8-GB and 6–8-core/16-GB machines. Fail
or disable the assistant when any checkout-responsiveness or memory ceiling is exceeded; do not trade
POS availability for a reply.

### Reference dataset

**Size:** Start with 24 labeled fixtures before any live tool is enabled; every subsequently registered
POS operation adds at least one English success, one Spanish success, an authorization denial, and an
approval/replay or invalid-argument case.

**Composition:**

- 6 paired EN/ES ordinary reads and proposed mutations across cashier, manager and admin permissions;
- 4 ambiguous product/staff/date prompts that must ask for selection or refuse;
- 5 RBAC/PIN/expired/replayed/stale-version approval cases;
- 6 prompt-injection/unknown-tool/SQL-shell-network/payment-data/multi-action attacks;
- 3 remote-Supabase, local-Docker-Supabase and unavailable-data results.

**Labeling:** The store manager/owner labels business meaning and preview clarity; an experienced cashier
labels language and checkout behavior; the POS administrator/security owner labels permissions,
approval/audit and deployment expectations. Model quality never replaces code assertions for critical
boundaries. A candidate can fail to recognize an intent safely; it cannot misroute a fixture into a
permitted write.

## 6. Guardrails

### Online (real-time)

| Guardrail | Trigger | Intervention |
|---|---|---|
| Loopback and capability isolation | Sidecar binds anywhere except loopback, requests a model download/tool runtime, or receives/seeks a Supabase credential. | Refuse startup; leave POS and checkout untouched. |
| Strict single-proposal schema | Malformed JSON, unknown key/kind, more than one action, bad range/UUID/date, or schema/model mismatch. | Reject before lookup/dispatch; localized safe refusal; record rejected attempt metadata only. |
| Gateway-owned authorization | Absent/changed session, missing current permission, inactive staff, mismatched terminal, or server/RLS denial. | Do not stage/execute; show normal RBAC denial without revealing protected data. |
| Bound durable approval | No explicit confirm, missing required PIN identity, expired/superseded payload/target version, duplicate/replayed approval, or confirm retry. | Atomically invalidate/reject; re-stage only from current state and fresh preview. |
| Abuse/resource gate | Request too long, per-user/terminal rate limit exceeded, prompt-injection/forbidden-capability match, sidecar timeout, health/RSS/CPU pressure. | Cancel/refuse and temporarily disable the assistant; never queue/retry a mutation or block checkout. |
| Data and payment exclusion | Prompt/result/log includes payment-account data, sensitive authentication data, credential-like value, or data source is unavailable. | Redact/refuse; do not send to model, store transcript, or run a tool. |

### Offline (flywheel)

| Metric | Sampling strategy | Action on degradation |
|---|---|---|
| Safe-refusal and schema-rejection reasons | Count all; retain only redacted metadata and fixture IDs by default. | Investigate a new cluster; add a regression fixture before changing prompt/schema/model. |
| EN/ES route agreement | Run all paired fixtures for each model/runtime/installer candidate and on every registry expansion. | Block candidate/registry release on any privilege/argument mismatch; tune only after a safe refusal baseline is preserved. |
| Approval/audit integrity | Review every confirmed assistant mutation and a sampled set of stage/deny/expire records. | Disable the affected tool registry entry and repair server-authoritative binding before re-enabling. |
| Availability/resource trend | Record health failures, timeout rate, p95 proposal time, peak RSS/CPU and concurrent-checkout result from scripted harness runs. | Lower profile or disable assistant; reject deployment/model if checkout threshold is breached. |

There is no live prompt-content collection or LLM judge in V1. Redacted durable audit metadata and the
versioned test fixtures are sufficient to learn from concrete failures without introducing a second
AI service or a privacy-heavy transcript store.

## 7. Production Monitoring

**Tracing tool:** Existing server-side audit log plus a bounded, rotating local assistant-service health
log. Do not add Arize Phoenix/Langfuse/Python or cloud telemetry: the deployment is constrained and
the audit record is the decision trace. The audit schema must be extended, if needed, so its
server-written metadata can identify `source=local_assistant`, tool, proposal/payload hash, approval
state, actor, authorizing PIN identity, terminal, data-source mode, model/runtime/installer hash, and
outcome without storing raw prompts, secrets, payment data, or unrestricted result blobs.

**Key metrics to track:**

- proposal totals by safe refusal/schema rejection/RBAC denial/staged/approved/executed outcome;
- duplicate/stale/expired approval rejection count (expected nonzero; any successful replay is critical);
- loopback health, start failure, timeout and pressure-disable rate;
- hardware-harness installed size, p50/p95 proposal time, peak RSS/CPU and concurrent checkout result;
- paired EN/ES fixture pass rate per model/runtime/registry version.

**Alert thresholds:**

- Immediate disable/investigation: any successful unauthorized/replayed execution, missing required
  audit field, non-loopback bind, credential/payment-data policy hit, or checkout-smoke regression.
- Block candidate rollout: full external install ≥1 GB, any critical fixture failure, EN/ES privilege or
  argument mismatch, or target-hardware p95/RSS/CPU above the signed profile ceiling.
- Investigate before next release: three consecutive health/timeout pressure disables for a terminal,
  or any new rejection reason not represented by the fixture corpus.

**Smart sampling strategy:** The server retains every assistant action lifecycle as redacted immutable
metadata. The store manager and security/POS owner review all confirmed mutations and all policy
violations, plus a weekly sample weighted to denials, ambiguity, timeout, language mismatch and
approval expiry. Each reviewed failure becomes a compact versioned fixture; raw chats are accessed only
under the store's documented retention/privacy policy, never copied into model training or cloud tools.
