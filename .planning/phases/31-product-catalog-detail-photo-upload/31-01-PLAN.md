  <decision>
Two decisions in this plan cannot be walked back cheaply. Confirm both before the migration is
written, then record the answers in the plan SUMMARY.

**Decision A — column name and stored-value shape (one-way).**
D-16 states the column holds a stable object path, not a URL, and explicitly leaves the *name* to
the planner: "the column holds a path, so `photo_path` reads truer than `photo_url`". PCAT-01..04
names the column `photo_url` verbatim in REQUIREMENTS.md.
Recommended default (31-RESEARCH.md A1): DB column `photo_path`, TypeScript field `photoPath`,
holding a bare object path such as `products/{productId}/{uuid}.webp`.
Why one-way: this repo has no DOWN scripts (CLAUDE.md), and switching between path semantics and
URL semantics later requires a data migration over every populated row plus a rewrite of the
resolver and every read site.

**Decision B — scope of the `storage.objects` SELECT policy (costly, near one-way).**
D-15 restricts *writes* to holders of `manage_products` but is silent on reads. D-14 lists cashier-facing
surfaces (checkout grid, cart) as future resolver consumers.

**Answer this with accurate information: no cashier-facing surface renders a product photo in this
phase.** Both resolver call sites phase 31 ships — the Photo panel in the product dialog (this plan)
and the catalog thumbnail column (Plan 03) — sit behind `manage_products` already. The four other
surfaces D-14 names render no image at all today (`grep -rln "<img" src/entities/tab
src/entities/inventory src/entities/open-unit src/entities/purchase-order src/widgets/ProductGrid`
returns nothing; see this plan's RECORDED DEFERRAL truth). So the looser SELECT policy delivers
**zero** display benefit inside phase 31 — its entire value is forward-looking, to the phase that
first puts an `<img>` on a cashier surface. Do not choose it believing it lights up photos at the
register this phase; it does not.

Recommended default (31-RESEARCH.md Open Question 1): SELECT is granted to the `authenticated` role
for `bucket_id = 'product-photos'` with **no** `manage_products` predicate; INSERT / UPDATE / DELETE
keep the `role_permissions` + `get_user_role()` + `manage_products` predicate. The `anon` role gets
nothing at all under either option.

What each choice actually costs, stated plainly so the trade is visible:
  - Looser (recommended default A): any authenticated staff member — including a cashier who can
    never upload — can mint a signed URL for any product photo starting today, buying nothing today,
    in exchange for cashier-facing display working later without a second migration.
  - Tighter (option B): read scope stays equal to write scope for as long as the read scope is
    unused, at the cost of one more forward migration plus a re-audit of the read path on the day a
    cashier surface first renders a photo.
The default stays A because product photos of packaged retail goods are low-sensitivity and this
repo ships no DOWN scripts, which makes the extra migration the more expensive side of the trade —
but pick A as a deliberate forward-looking bet, not as a phase-31 requirement. Choosing B costs this
phase nothing.

**Also confirm before writing the migration (not a design decision, an environment fact —
31-RESEARCH.md Open Question 2 / A3):** whether a `product-photos` bucket already exists on the
target Supabase project with different settings. Check with
`supabase.storage.getBucket('product-photos')` through the E2E service client, or the Studio
Storage dashboard. If one exists with different settings, the conflict-tolerant insert in Task 2
silently leaves the wrong configuration in place and the migration must instead update the existing
row.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer → Supabase Storage API | An anon-key client uploads binary content; everything it claims (MIME type, size, target path) is attacker-controllable through devtools |
| renderer → `products` table | The path column is written by the client; a forged value would point every reader at an arbitrary object key |
| Storage object → `<img src>` | Signed URLs leave the app and can be replayed for their whole TTL |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-01 | Elevation of Privilege | `storage.objects` write policies for `product-photos` | high | mitigate | INSERT/UPDATE/DELETE policies carry `bucket_id = 'product-photos' AND EXISTS (SELECT 1 FROM role_permissions WHERE role = get_user_role() AND action = 'manage_products')`, granted `TO authenticated` only; the client-side gate is UX. Proven by the cashier-denial spec in Plan 05. |
| T-31-02 | Tampering | client-side file validation | high | mitigate | Bucket-level `allowed_mime_types` (three image types) and `file_size_limit` 2097152 are enforced by the Storage server regardless of what the client claims; Task 2 acceptance asserts both through `getBucket`. |
| T-31-03 | Tampering | Storage object key construction | high | mitigate | `photoObjectPath` mints `products/{productId}/{uuid}.{ext}`; `File.name` is never read into the key, so a `../` filename cannot escape the product's prefix. |
| T-31-04 | Information Disclosure | private-bucket read scope | medium | mitigate | Bucket visibility is off and all four policies are granted `TO authenticated`; `anon` gets nothing. Reads go through short-lived signed URLs. |
| T-31-05 | Information Disclosure | signed-URL replay after a photo is replaced | medium | mitigate | 1-hour TTL; replace writes a new uuid key and deletes the old, so a leaked URL for the replaced photo resolves to a deleted object instead of continuing to serve. |
| T-31-06 | Denial of Service | canvas decode of a crafted high-dimension image | low | accept | 10 MB pre-resize cap plus the 2 MB bucket cap bound the stored artifact; a crafted large-dimension image can still stall the renderer, accepted because this surface is admin-only behind PIN auth on a single-store terminal. |
| T-31-07 | Repudiation | provenance of a photo change | low | accept | The path column is an ordinary `products` column change and inherits whatever audit coverage `products` already has; this phase adds no new audit surface. |
| T-31-SC | Tampering | npm/pip/cargo installs | low | accept | No packages are installed by this phase — 31-RESEARCH.md § "Package Legitimacy Audit" records it as not applicable (native Canvas plus the already-installed `@supabase/supabase-js`). Task 2 acceptance asserts `package.json`/`package-lock.json` are untouched. |
