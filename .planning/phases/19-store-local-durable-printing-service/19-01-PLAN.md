<objective>
Prove the entire store-local durable printing architecture end-to-end on ONE job type (`test_print`)
before expanding to the other three: a Tauri command hits a brand-new standalone Rust `broker/` crate
over authenticated HTTP, the broker durably commits the job to a WAL SQLite ledger before acknowledging
it, an independent worker tick delivers it to a named Windows printer queue via the proven
`OpenPrinterW`/`StartDocPrinterW`/`WritePrinter` sequence, and ambiguous/failed/restart-mid-flight
outcomes are handled exactly as Spike 001 validated on real hardware — never as a silent success.

Purpose: Spike 001 (`.planning/spikes/001-windows-print-broker/`) already proved this architecture works
on real Windows Service infrastructure and a real thermal printer. This plan turns the spike's single
`broker/src/main.rs` into the production crate's module skeleton (`ledger.rs`, `http.rs`, `delivery.rs`,
`main.rs`) and wires exactly one existing caller (`HardwareSettingsTab`'s Test Print button) through it,
so any architectural mismatch surfaces after one small caller, not after all four are migrated.
Output: A running `broker/` crate (foreground binary, not yet a registered Windows Service — that is
Plan 19-02's job) that durably accepts, delivers, and reconciles `test_print` jobs; `pos-printer.ts`'s
`testPrint()` now returns a broker-issued job ID; new `AppErrorCode` values for broker-specific failures.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| LAN client -> broker HTTP (POST /jobs, GET /jobs/{id}, GET /health) | untrusted network input crosses here — any device on the network holding or guessing the bearer secret |
| Tauri command layer -> broker | localhost-bound HTTP call that carries the per-store bearer secret |
| broker -> SQLite ledger | local-disk, single-process trust boundary |
| broker -> Windows Print Spooler (WinSpool) | local OS API boundary; printer driver/queue behavior is only partially trusted (spike found a stuck-queue class of fault) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-01 | Spoofing | broker/src/http.rs auth check on every route | high | mitigate | Bearer secret compared before any DB touch, ported verbatim from the spike's proven 401-before-DB-touch behavior; the hardcoded dev-only fallback secret in this plan is replaced by a per-store generated one in Plan 19-02 |
| T-19-02 | Tampering | broker/src/http.rs payload_b64/idempotency_key/printer_name validation | medium | mitigate | Malformed base64, empty required fields, and malformed JSON are all rejected 400 before any SQLite INSERT, ported from the spike's proven validation order |
| T-19-03 | Denial of Service | Tauri->broker connect call with no timeout | high | mitigate | reqwest connect_timeout(1500ms) (D-12) prevents an unreachable broker from hanging the print/checkout flow indefinitely — closes Pitfall 4's proven ~2s+ silent-hang case |
| T-19-04 | Information Disclosure | bearer secret custody | medium | mitigate | The broker HTTP client stays entirely in the Rust command layer (src-tauri), never the frontend — the secret never reaches the webview/devtools-inspectable JS bundle |
| T-19-05 | Repudiation | append-only events table | low | accept | Every state transition is logged with a timestamp; deeper tamper-evidence (hash chaining) is not required at this project's ASVS L1 scope |
| T-19-SC | Tampering | broker/Cargo.toml crate installs (rusqlite, tiny_http, uuid, base64, windows) | high | mitigate | All five crates are OK/Approved in 19-RESEARCH.md's Package Legitimacy Audit table (no [ASSUMED]/[SUS] entries) — no blocking-human checkpoint required for this task |
