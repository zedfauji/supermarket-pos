<objective>
Stand up the entire backend surface for bank-transfer payment tracking as one proven, real, end-to-end
slice: the `payment_method` enum gains `bank_transfer`, a new `bank_transfers` sibling table (mirroring
`refunds`) tracks the pending/confirmed/disputed reconciliation state, the existing checkout RPC chain
(`process_direct_sale_atomic` -> `process_payment_atomic`) accepts `bank_transfer` and generates the
7-digit Luhn reference code server-side, and two new manager+-gated RPCs
(`confirm_transfer_payment`/`dispute_transfer_payment`) mirror `process_refund`'s exact
auth/audit shape. RBAC actions and audit action strings are registered before any SQL references them
(Pitfall 1). Every one of the three state transitions calls `record_audit()` in the same transaction
(D-09), and this plan introduces zero bank-statement import, PSP webhook, or bank-API client anywhere
(D-04 — ruled out permanently by the user, not merely deferred). No UI exists yet — this plan is
verified by a real RPC integration test hitting the live Supabase project, proving the backend half of
"mark pending -> confirm/dispute" end-to-end per D-01 through D-10.

Purpose: every later plan in this phase (checkout UI, reconciliation UI, CSV export, reporting) builds
on this schema/RPC contract; getting it right once, proven against a real database, avoids retrofitting
plans 02-05 around a backend design that changes shape later.

Output: `bank_transfers` table, 2 new RPCs, `payment_method` enum extended, RBAC + audit action
registries updated, Zod domain types, and a green RPC integration test.
</objective>

  <decision>How should `payments.method` represent a bank-transfer sale — extend the existing `payment_method` Postgres ENUM, or something else?</decision>
  <context>
    `payment_method` (verified this session, `src/shared/lib/supabase.types.ts:1924`) is a genuine
    Postgres ENUM type (`cash | card | rappi | tab_transfer`), not a text+CHECK column like
    `payments.status`. Adding an ENUM value is a one-way door: Postgres has no `ALTER TYPE ... DROP
    VALUE` — once any `bank_transfer` payment row exists in production, removing the value requires a
    full type rebuild (recreate the type without the value, migrate every dependent row/column). This
    is exactly the "on-disk/wire format ... a schema other systems already read" one-way case per
    the reversibility taxonomy, and RESEARCH.md's Pitfall 4 flags the transaction-ordering hazard on
    top of that. This decision was not one of CONTEXT.md's locked D-01..D-17 items — RESEARCH.md's
    "Primary recommendation" proposes Option A but leaves it as a planner-level call, not a
    user-confirmed one.
  </context>
  <options>
    <option id="enum-extend">
      <name>Add `'bank_transfer'` as a new `payment_method` ENUM value (RESEARCH.md's recommendation)</name>
      <pros>Consistent with how cash/card/rappi are already represented; every existing method-keyed
      query (`get_payment_methods_report`'s `GROUP BY p.method`, `get_caja_report`'s per-method sums)
      picks up the new value with minimal changes; smallest, most consistent schema change.</pros>
      <cons>One-way: cannot be removed once rows exist without a full ENUM type rebuild + data
      migration.</cons>
    </option>
    <option id="text-check">
      <name>Convert `payments.method` from ENUM to `text` + CHECK constraint in this same migration</name>
      <pros>Future method additions become cheap/reversible (redefine the CHECK, no type rebuild
      ever again).</pros>
      <cons>Touches every existing query/cast against the ENUM type across the whole payments/reporting
      surface for a reason unrelated to this phase's scope — a much larger, riskier migration than
      BTP-01..10 calls for, and still doesn't undo the *decision* to add bank_transfer, only makes the
      *next* one cheaper.</cons>
    </option>
    <option id="boolean-flag">
      <name>Keep `payments.method` at `'card'` (or similar) for a bank-transfer sale and add a new
      `is_bank_transfer boolean` column instead</name>
      <pros>Never touches the ENUM type at all — fully reversible (drop the boolean column later).</pros>
      <cons>Semantically wrong: `method` would misreport how the sale was actually paid, breaking
      BTP-10's requirement that `get_payment_methods_report` show bank-transfer as its own bucket, and
      repeats the exact anti-pattern RESEARCH.md's Pitfall 2 warns against (overloading an existing
      column with a second, orthogonal meaning).</cons>
    </option>
  </options>
  <resume-signal>Select: enum-extend, text-check, or boolean-flag (default recommendation: enum-extend)</resume-signal>
