<objective>
Close the folded todo (`.planning/todos/pending/audit-manager-pin-identity-in-remaining-rpcs.md`):
`process_refund` already accepts `p_manager_pin` but ignores it (checks the caller's own `auth.uid()`
session role instead); `reopen_tab`/`edit_paid_tab` have no `p_manager_pin` parameter at all and make
the same `auth.uid()` mistake; `close_tab` has zero authorization check of any kind despite being a
live, `GRANT EXECUTE ... TO authenticated` PostgREST endpoint. This is a confirmed, reproducible bug
(the exact G-27-13 failure mode already fixed once for `process_direct_sale_atomic` in Plan 27-08) —
not an investigation, a mechanical repeat of that proven fix across three more RPCs, plus hardening a
fourth that has no check to begin with.

Purpose: Close a real elevation-of-privilege gap where a cashier who gets a genuine manager to type
their PIN into `ManagerPinDialog` is still incorrectly denied (because the RPC re-checks the cashier's
own role, not the entered PIN's), and where any authenticated staff member can bypass `close_tab`'s
role intent entirely via a direct RPC call.
Output: One migration re-keying `process_refund`/`reopen_tab`/`edit_paid_tab`'s authorization to the
entered PIN and adding a role gate to `close_tab`; three dialogs' `ManagerPinDialog` consumers widened
to thread the matched staff's PIN through; four new/extended automated tests proving both the fix and
the close_tab hardening.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Cashier session -> process_refund/reopen_tab/edit_paid_tab RPCs | A privileged-override action gated by a manager/admin PIN entered into a client dialog; the server must independently re-derive the authorizing identity, never trust the caller's own session role for this specific override |
| Any authenticated session -> close_tab RPC | A direct PostgREST-reachable endpoint with no UI wiring today, but still a live attack surface regardless of UI absence |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-28-04 | Elevation of Privilege | process_refund / reopen_tab / edit_paid_tab | high | mitigate | Re-derive the authorizing staff from `profiles.pin = p_manager_pin` joined to `role_permissions`, independently of `auth.uid()`'s own session role — the exact G-27-13 pattern already proven for `process_direct_sale_atomic` (T-27-10). |
| T-28-05 | Elevation of Privilege / Tampering | close_tab | high | mitigate | Add a `role IN ('manager','admin')` gate as the first statement in the function body, closing a previously zero-checked `GRANT EXECUTE ... TO authenticated` endpoint reachable by any authenticated staff member via a direct RPC call. |
</threat_model>
